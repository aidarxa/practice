## Цель и согласованные границы

- Полностью заменить SYCL на PCUDA: ядра, память, управление выполнением, загрузку данных, служебные GPU-операции и ручные примеры SSB.
- Сохранить Data-Centric Push-модель, Predicate Pushdown и Kernel Fusion внутри каждого ядра.
- Отдельно компилировать и загружать специализированные ядра; не перелинковывать библиотеку всего запроса при изменении одного ядра.
- Отделить структуру SQL-запроса от значений параметров. После подготовки шаблона смена совместимых значений не вызывает codegen, `acpp` или линкер движка.
- Сохранить работающую SQL-функциональность, исправляя обнаруженные ошибки NULL/3VL в переносимых путях. Не считать ошибочное поведение старого движка эталоном.
- Провести рефакторинг настолько глубоко, насколько требуется для этих целей, но не включать автоматически новые SQL-возможности и полную замену всех алгоритмов.
- Кеш скомпилированных SQL-модулей нужен только внутри процесса. PCH и универсальные служебные ядра подготавливаются при сборке/установке.
- Динамические PCUDA-модули: C++17, `--acpp-targets=generic --acpp-pcuda`, `-O0`. Обычный host-код движка остаётся в Release.
- Обязательная аппаратная приёмка — AMD GPU. Сохранять переносимость на NVIDIA/Intel в рамках поддержки AdaptiveCpp, без неподтверждённых обещаний тестирования на этих устройствах.

### Что означает повторное использование

| Изменение | Требование |
| --- | --- |
| `WHERE a > 10` → `WHERE a > 15` | Тот же шаблон и модули; меняется значение параметра |
| Числовые значения в арифметике, HAVING, CASE и LIMIT при совместимых типах | Runtime-параметры, включая необходимые расчёты размеров и выбор подготовленных алгоритмов |
| `WHERE a > 10` → `WHERE a < 10` | Изменение структуры; допустима компиляция затронутых ядер |
| `ORDER BY 1` → `ORDER BY 2`, если меняется выбранная колонка | Изменение логики после разрешения SQL-позиции, не обычный параметр |
| `10` → `10.5` или замена на NULL | Согласован lazy typed (до 8 вариантов на структуру ядра) + один tagged fallback. Смена типа может компилировать отсутствующую схему; typed NULL меняет validity без компиляции. Первый нетипизированный NULL выводится из контекста либо сохраняет NULL-only форму без гарантии переиспользования при замене на число. |

Это гарантия SQL JIT движка. Внутренний device JIT/специализации AdaptiveCpp учитываются отдельно; отсутствие новой работы device JIT не обещано.

## Отправная точка до этапа 5 (историческая)

- `src/core/execution.cpp`: ядра запроса всё ещё компилируются в одну `.so`; legacy-кеш зависит от исходной SQL-строки. После этапа 2 библиотека содержит отдельные kernel wrappers без host-алгоритма запроса, а выполнение определяется физическим планом/runtime. Frontend оптимизирует параметризованное дерево и связывает отдельную literal-копию; новый ключ логического шаблона не подменяет value-dependent ключ старой библиотеки. `FileBasedQueryCache` фактически хранит карту путей в памяти процесса.
- `include/core/visitor.h`, `src/core/visitor.cpp`: Push-модель, несколько pipeline, PHT и MHT уже есть. Старый roadmap об их первоначальном внедрении больше не актуален.
- `Pipeline` не равен автоматически единице компиляции. На этапе 2 MHT prefix-sum и прежние дополнительные запуски из `includes_and_globals`/`post_execution_code` извлечены в реальные kernel contracts и операции плана; старые host-code streams удалены.
- `GROUP BY CASE` использует значения ветвей в расчёте домена и генерации хеш-функции; LIMIT влияет на генерацию Top-K и сортировки.
- После этапа 3 `ExecutionContext`, `DynamicDeviceBuffer`, загрузчик и sparse-fetch используют PCUDA-owned ресурсы. SYCL остаётся в старых device bodies/примитивах и удаляемом launch-view на том же executor; постоянный гибрид не вводится.
- Незакоммиченные эксперименты пользователя с PCH/PCUDA не перезаписывать и не удалять при переносе.

## Целевая модель

```text
SQL / AST
  → разрешение колонок, aliases и SQL-позиций
  → структура запроса + параметры
  → оптимизированный план
  → явный физический план выполнения
  → поиск модулей в кеше процесса
  → генерация и компиляция только отсутствующих специализированных ядер
  → модули PCUDA + заранее собранные служебные ядра
  → выполнение в одном явном упорядоченном stream
  → получение типизированного результата
```

### Единица компиляции и ABI

- Одно фактическое GPU-ядро и его host-обёртка запуска компилируются в одной единице трансляции; специализированный модуль — отдельная `.so`.
- Не разбивать fused pipeline на отдельные SQL-операторы. Например, ручной Q3.3 сохраняет три build-ядра и одно слитое probe/aggregate-ядро.
- Движок управляет буферами, размерами, зависимостями, runtime-ветвлениями и материализацией. Модуль ядра не исполняет весь запрос и не владеет памятью запроса.
- Универсальный ABI: фиксированная C-сигнатура, версионируемый POD-контекст, handle stream, конфигурация запуска, указатели, размеры, параметры и код результата; без STL и SYCL-объектов.
- Планировщик формирует схему аргументов вместе с ядром. План хранит привязку слотов к колонкам/буферам/параметрам; обёртка знает конкретные типы; загрузчик проверяет ABI и схему. Движок не угадывает ожидаемые данные через `dlsym`.
- Точные имена, сигнатура и layout ABI v1 утверждены на этапе 2: `include/core/module_abi.h`, `db_kernel_descriptor_v1` / `db_kernel_launch_v1`, C11/C++ layout assertions. Этап 5 подключил отдельные PCUDA-модули с этими entry names и identity entry; прежний индексированный legacy bundle больше не генерируется.

**Компромисс:** отдельные `.so` устраняют перелинковку всего запроса, но несколько запусков компилятора имеют накладные расходы. Раздельная компиляция сама по себе не гарантирует меньший cold latency; это проверяется на этапе 0 и при окончательной приёмке.

**SQL→PCUDA ≤10 мс — отдельный согласованный целевой бюджет для проверки при

существующий `prepare_ms` включает также runtime-работу и не равен чистой трансляции.

Абсолютные cold/warm-цели **полного SQL-пути** Q3.3 и остальных SSB согласовать
отдельно на интегрированном пути до окончательной приёмки этапа 8. Это не блокирует
закрытие этапа 0 по принятой пользователем ограниченной области. Ни 600 мс,
ни прежние 80%/110% автоматически на полный SQL не распространяются;
процентные пороги пользователь не утвердил. Корректность всех 13 SSB и действующего

## Этап 9 (дополнительный, необязательный). Replay компилятора и линкера

До этого используется штатный `acpp`; результаты эксперимента не означают готовую интеграцию.
Основание: [PERF-COLD](test/pcuda_compile_perf/REPORT.md), разделы 2, 4.6 и 4.9.

**Техника:** один раз при подготовке конфигурации получить effective Clang argv

запускать эти команды для новых исходников/объектов. Реальная компиляция и отдельная
`.so` на ядро сохраняются: это обход повторной работы драйверов, **не кеш готовых
SQL-модулей**. Не выполнять discovery/dry-run заново на каждом запросе.

| Replay Clang/LLD, 4 цепочки | 37,972 | 371,793 | 8,583 | 8,541 |

## Согласованные и открытые решения

1. **Смена типов параметров — согласовано:** lazy typed, до 8 вариантов на структуру ядра, затем один tagged fallback; готовые typed-модули переиспользуются. Смена типа может вызвать компиляцию отсутствующего варианта/fallback. См. [архив D](test/pcuda_stage0/REPORT.md#stage0-types) и контроль четырёх независимых параметров.
2. **NULL-параметры — согласовано:** известный тип слота сохраняется, меняется validity без компиляции; первый NULL получает тип из однозначного контекста, иначе сохраняет NULL-only форму. Для NULL-only → число новая схема допустима. SQL NULL/3VL-функциональность сохраняется; её исправления входят в перенос.
3. **Численные показатели этапа 0 — согласовано 2026-10-31:** [абсолютные цели](#performance-targets) 600/200/10/9 мс для Q3.3 SF10/V2 через acpp/parallel4; бюджет SQL→PCUDA ≤10 мс проверить при интеграции. Полные SQL cold/warm-цели согласуются отдельно до приёмки этапа 8 и не блокируют этап 0. Прежние процентные пороги не утверждены; пользовательский ориентир 500 мс компиляции не является SLA SQL.
4. **Replay — отложен по решению пользователя:** только необязательный этап 9, если останется время после этапов 1–8; сейчас не внедрять. Измерения, техника и риски сохранены выше и в [PERF-COLD](test/pcuda_compile_perf/REPORT.md).
5. **Числовые параметры этапа 6 — согласовано 2026-11-08:** SUM/MIN/MAX возвращают Int64 либо Float64 входного выражения, COUNT — UInt64, AVG — Float64. Минус перед числовым литералом нормализуется как часть значения; общий унарный оператор не добавлялся. Числовой GROUP BY CASE остаётся integer/NULL; согласованное Text CASE-расширение — следующий пункт 7.
6. **Текстовая граница этапа 7 — согласовано 2026-11-08:** пользователь отверг словарные числовые коды и выбрал сейчас только план отдельного расширения 7-TEXT, затем основной перенос. До его реализации text SQL/stars явно отклоняются без raw-Int32; ASCII byte-флаги декодируются в Int32 0/1, физическая DDATE-схема исправлена. Строковые типы, операции, padding/collation и ABI согласуются отдельно перед кодом. Пять действующих manifest-форм с текстом не становятся `future` или успешными тестами из-за этой границы.
7. **7-TEXT — согласовано 2026-11-10, функционально выполнено 2026-11-11:** единый UTF-8 Text, полный предложенный набор, бинарное сравнение/значимые пробелы/отдельный NULL, bounded NUL и запрет implicit conversion, NUL/invalid UTF-8/SUM/AVG Text. ABI v2 и runtime ownership описаны отдельно; custom2 использует BUILDING/FURNITURE. Пять прежних отказов теперь проверяются как реальные результаты, а исторические failures сохраняются. Этап 8/performance targets и `future` не закрываются автоматически.

Изменение этих решений и существенные отступления от плана сначала обсудить с пользователем.
