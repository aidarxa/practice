# Можно ли выполнять запрос сразу, а оптимизировать его после ответа?

## 1. Что удалось проверить и каков ответ

Это отчёт исследования многоуровневой компиляции **JIT-TIER**.
Эксперименты проведены **31 октября 2026 года**
на AMD Radeon 780M. **1 ноября 2026 года текст переписан для понятного чтения;
измерения, результаты и ограничения не менялись. Новых экспериментов при
переписывании не проводилось.**

Исходный вопрос: можно ли сначала быстро вычислить запрос, вернуть ответ,
а уже потом незаметно для пользователя подготовить более быстрый вариант кода?

Для начала определим четыре сокращения:

- **GPU — Graphics Processing Unit**, графический процессор, или видеопроцессор.
  Здесь он обрабатывает строки таблиц и считает результат запроса.
- **CPU — Central Processing Unit**, центральный процессор компьютера.
  Здесь на нём работает приложение, запускается компилятор и принимается результат.
- **SQL — Structured Query Language**, язык запросов к базе данных.
- **JIT — Just-In-Time**, компиляция во время работы приложения.
  В нашем случае она превращает ещё не готовую для конкретной видеокарты
  программу в код, который эта видеокарта может выполнить.

### 1.1. Короткий ответ

Компиляция переводит программу в другую форму, в конечном счёте — в **машинный
код**, то есть инструкции, которые процессор может выполнить непосредственно.
Оптимизация меняет способ вычислений, чтобы программа работала быстрее,
сохраняя требуемый результат.

**Отложить обязательное получение исполняемого кода нельзя: без него новый
запрос нечем вычислять. Но можно сначала подготовить базовый исполняемый вариант,
а более быстрый подготовить после ответа.**

Искомая схема выглядит так:

```text
Запрос → подготовка базового кода → вычисления → ответ пользователю
                                                    ↓
                                  фоновая подготовка улучшенного кода
                                                    ↓
                             следующие запуски используют улучшенный код
```

Такой подход называется **многоуровневой компиляцией**: у одной программы
есть несколько исполняемых вариантов с разной ценой подготовки и скоростью работы.

Мы сделали проверочный прототип — **PoC, Proof of Concept**, то есть небольшую
программу для проверки самой идеи, а не готовую функцию базы данных.
Он показал следующее:

1. **Подготовить второй вариант после первого ответа возможно.** Прототип сначала
   получает результат, затем в отдельном потоке начинает подготовку улучшенного
   кода. Поток — это отдельная последовательность работы внутри того же приложения.
2. **Фоновая работа пока мешает следующему запросу.** Уже подготовленный запрос
   обычно занимал около **0,13 мс**, но при попадании на фоновую компиляцию —
   **34,61 мс**. Причина связана с тем, как AdaptiveCpp хранит готовые программы
   и разрешает обращаться к ним из разных потоков. Почему это относится к вопросу
   о «незаметном» фоне, подробно объяснено в разделе 4.4.
3. **Меньше оптимизаций не обязательно означает более быстрый первый ответ.**
   В одном из проверенных вариантов первый ответ на запрос Q3.3 стал занимать
   **972,40 мс** вместо штатных **468,36 мс**, а повторное исполнение —
   **143,08 мс** вместо **8,08 мс**. Причины и различия вариантов разобраны ниже.

**Итог:** идея работоспособна, но в проверенной версии AdaptiveCpp её нельзя
получить одним параметром компилятора или простым переносом работы в поток.
Нужны действительно дешёвый базовый вариант и возможность готовить улучшенный
вариант, не задерживая обращения к уже готовому коду.

### 1.2. Что именно проверено, а что — нет

Исследование продолжает [предыдущую работу о времени первой компиляции — PERF-COLD](../pcuda_compile_perf/REPORT.md).
Новые программы работают отдельно от движка базы данных.

Есть два разных испытания:

- **Q3.3** — один из аналитических запросов из набора тестов базы данных.
  Он нужен для проверки времени на большой таблице.
- **Небольшой пример с отбором строк и вычислением выражения** — для проверки
  последовательности «первый результат → фоновая компиляция → использование
  нового варианта». Его время нельзя сравнивать с Q3.3 как одну и ту же нагрузку.

**В обоих случаях измеряется прототип, а не весь путь от текста SQL до ответа.**
Прототип не разбирает SQL, не строит план запроса — описание нужных операций —
и не генерирует исходный код:
исходники вычислений для него уже подготовлены. Эти ограничения важны для чтения
всех чисел в отчёте.

Прототип также не показывает ответ сетевому клиенту. Его точка «ответ готов» —
момент, когда результат уже находится в памяти центрального процессора и может
быть прочитан приложением.

В рамках исследования **не менялись** движок, установленный AdaptiveCpp,
пользовательские опыты с компилятором и исходные незакоммиченные изменения.
Этапы переноса 1–8 не реализованы этим исследованием. Согласованные ранее
показатели **600/200/10/9 мс** для ограниченного тестового стенда остаются прежними;
их точный смысл и область приведены в [todo.md](../../todo.md#performance-targets).

## 2. Как здесь устроена компиляция и на чём проводилась проверка

### 2.1. Почему компиляция происходит дважды

**AdaptiveCpp** — используемая система компиляции и выполнения программ для
центральных и графических процессоров. Команда **`acpp`** запускает её компилятор.

В исследовании используется **PCUDA — AdaptiveCpp Portable CUDA**: способ писать
GPU-программы на C++, которые AdaptiveCpp может приспособить к разным устройствам.
Здесь **ядро** — одна такая функция для параллельной обработки данных на видеокарте.

Путь состоит из двух этапов:

| Этап | Когда выполняется | Что получается |
| --- | --- | --- |
| Первый | Когда приложение вызывает `acpp` для созданного исходника | Код вызова ядра со стороны CPU и промежуточное описание самого GPU-ядра |
| Второй | При первом запуске ядра, когда уже известно конкретное устройство | Машинный код, подходящий выбранной видеокарте |

**Промежуточный код**, или **IR — Intermediate Representation**, — это форма
программы для дальнейшей обработки компилятором. В нашем случае это LLVM IR.
Он ещё не является инструкциями выбранной видеокарты.

**LLVM** — название набора библиотек и инструментов для создания компиляторов.
Здесь он обрабатывает промежуточный код, оптимизирует его и участвует в получении
машинного кода. **Clang** — компилятор C/C++ из этого набора, которым пользуется
AdaptiveCpp.

В исходниках и журналах эти этапы могут называться:

- **S1 — Stage 1**, первый этап: обработка C++ и подготовка промежуточного кода;
- **S2 — Stage 2**, второй этап: подготовка кода для конкретного устройства.

**S2 — не название отдельной оптимизации.** Это весь второй этап, в котором
есть и оптимизации, и обязательная работа по получению исполняемой программы.
Дальше в тексте используется понятное название «второй этап компиляции».

В режиме **`generic`** промежуточный код сохраняет переносимость между
устройствами. Поэтому после первого этапа работа компилятора ещё не закончена.
Режим выбирается параметром `--acpp-targets=generic`.

Важное уточнение: **вторая компиляция здесь тоже выполняется на центральном
процессоре**. После неё готовый код загружается на видеокарту для вычислений.

### 2.2. Что находится в скомпилированном файле

Для каждого ядра создаётся отдельный файл **`.so` — shared object**, динамическая
библиотека Linux. Приложение может загрузить такой файл во время своей работы.
Такой отдельно собранный файл ядра мы называем **модулем**.
Здесь в нём находятся код вызова ядра со стороны CPU и промежуточный код для GPU.
**Наличие `.so` ещё не означает, что машинный код для видеокарты уже готов.**

При сборке разделяются две операции:

- **Компиляция** переводит исходник C++ в объектный файл `.o` — результат,
  который ещё нужно связать с требуемыми библиотеками.
- **Линковка**, или компоновка, связывает объектный файл с библиотеками и создаёт
  загружаемый `.so`. Программа для этой операции называется **линкером**.
  Здесь используется **LLD**, линкер из проекта LLVM.

Приложение загружает `.so`, находит функцию запуска и вызывает её. При первом
вызове AdaptiveCpp может начать второй этап компиляции. Именно это дополнительное
ожидание и было предметом исследования.

### 2.3. Почему `acpp -O0` не убирает ожидание перед вычислениями

**`-O0`** отключает большинство необязательных оптимизаций в конкретном запуске
компилятора.
**`-O3`** включает более широкий набор обычных оптимизаций; **`-O1`** —
промежуточный уровень. Эти параметры не отменяют обязательную компиляцию
и не передаются автоматически всем компиляторам, которые будут вызваны позднее.

В проверенной установке работа распределена так:

```text
Исходник PCUDA на C++
    ↓ acpp -O0
Библиотека .so с промежуточным кодом
    ↓ первый запуск ядра
Подготовка промежуточного кода к выбранной видеокарте
    ↓
Оптимизатор LLVM внутри AdaptiveCpp: уровень O3
    ↓
Отдельная программа opt: уровень O3
    ↓
Библиотеки AMD hipRTC/COMGR: получение готового машинного кода
    ↓
Загрузка кода на видеокарту → вычисления → результат в памяти CPU
```

Названия в нижней части схемы означают следующее:

- **`opt`** — отдельная программа LLVM для оптимизации промежуточного кода.
- **HIP — Heterogeneous-compute Interface for Portability**, программный
  интерфейс для работы с ускорителями. В этой установке используется его
  реализация AMD.
- **hipRTC — HIP Runtime Compilation**, библиотека для компиляции во время
  работы приложения. Здесь AdaptiveCpp передаёт ей промежуточный код.
- **COMGR — Code Object Manager**, компонент AMD, участвующий в создании
  и связывании машинного кода. Он работает внутри этого пути hipRTC.
- **Среда выполнения**, по-английски *runtime*, — библиотеки, которые во время
  работы приложения управляют устройством, памятью, запуском и готовым кодом.
  Это не ещё один пользовательский SQL-запрос.

Таким образом, `-O0` у первого `acpp` **не выключает последующие оптимизаторы**.
В частности, в рассмотренном коде ROCm 6.1.2 завершающая сборка через COMGR
получает собственный `-O3`. **ROCm** — программная платформа AMD для вычислений
на графических процессорах; hipRTC и COMGR входят в используемый здесь набор
её компонентов.

Даже если уменьшить оптимизации, нельзя просто пропустить всю оставшуюся работу.
Нужно выбрать нужное ядро, связать вызываемые им функции, учесть особенности
памяти устройства и превратить промежуточные операции в инструкции видеокарты.
Некоторые функции при этом обязательно встраиваются в вызывающий код — это
преобразование называется *встраиванием функций*, или *inlining*.

**Вывод для исходной идеи:** после `acpp -O0` у нас ещё нет базового машинного
кода для видеокарты. Сначала придётся получить хотя бы его. И только подготовку
более быстрого варианта можно будет отложить до следующего запуска.

### 2.4. Компьютер, версии и параметры сборки

Испытания выполнены на Ryzen 7 7840HS и AMD Radeon 780M, обозначение устройства
`gfx1103`. Оперативной памяти — около **30 ГиБ**; 1 ГиБ — `2^30` байт.
Проверка устройства подтвердила поддержку 64-битных вещественных чисел и
64-битных атомарных операций — неделимых обновлений значений из разных потоков.
На NVIDIA и Intel аппаратных проверок не было.

**SSB — Star Schema Benchmark** — набор аналитических запросов к таблицам
схемы «звезда». **Q3.3** — один из его запросов. **SF10 — Scale Factor 10** —
обозначение масштаба тестовых данных, а не размера файла в гигабайтах.
В этом наборе большая таблица содержит **59 986 217 строк**. Прототип Q3.3
использует четыре ядра и 24 группы результата, как в предыдущем исследовании.

Полный движок пока использует **SYCL** — стандарт программирования
разнородных вычислительных устройств на C++. Новые PCUDA-программы в этом
исследовании не являются уже выполненным переносом движка.

Для ускорения сборки использовался **PCH — Precompiled Header**, заранее
обработанный компилятором заголовочный файл. Он позволяет не разбирать одни
и те же C++-заголовки заново при сборке каждого ядра. PCH готовился отдельно,
до измеряемых запросов.

### 2.5. Где проверено устройство компилятора

Это не предположение, сделанное только по времени первого запуска.
Прочитаны исходники установленной версии и записаны фактические вызовы
инструментов во время работы прототипа.

- [Описание двух этапов компиляции AdaptiveCpp](https://github.com/AdaptiveCpp/AdaptiveCpp/blob/5989e1cfa4e70d55c65e786a4c71acb124ce54ff/doc/compilation.md#generic-sscp-compilation-flow---acpp-targetsgeneric)
  и [документация PCUDA](https://github.com/AdaptiveCpp/AdaptiveCpp/blob/5989e1cfa4e70d55c65e786a4c71acb124ce54ff/doc/pcuda.md)
  объясняют, зачем промежуточный код превращается в код устройства при запуске.
  В названии раздела документации встречается **SSCP — Single-Source Single
  Compiler Pass**: способ обработки общего исходника для CPU и GPU за один
  проход исходного компилятора. Это не означает, что второй этап не нужен.
- [Функция подготовки промежуточного кода `prepareIR` и внутренний оптимизатор O3](https://github.com/AdaptiveCpp/AdaptiveCpp/blob/5989e1cfa4e70d55c65e786a4c71acb124ce54ff/src/compiler/llvm-to-backend/LLVMToBackend.cpp#L256-L503)

## 3. Как проводили эксперименты

### 3.1. Откуда и докуда измеряли время

Основной показатель — **`summary`, время первого ответа в уже загруженной базе**.
В прототипе это один непрерывный интервал:

```text
Исходные таблицы уже загружены
    → подготовка данных и памяти именно для этого запроса
    → нужные компиляция и линковка
    → загрузка библиотек ядер
    → первое исполнение, включая второй этап компиляции, если он нужен
    → копирование результата в память CPU и ожидание готовности
```

Здесь используется **вторая версия методики, V2**, из предыдущего исследования:
подготовка памяти запроса входит в `summary`. Само приложение, загрузка исходных
таблиц и подготовка общего заголовка PCH выполняются раньше.
Проверка правильности, форматирование и печать результата — позже.

Напомним ограничение: в прототипе **нет разбора SQL, построения плана и генерации
исходника**, поэтому его `summary` не является временем полного SQL-запроса.

Другие показатели отделены от `summary`:

| Показатель в таблицах | Что он означает |
| --- | --- |
| Компиляция | Длительность вызова `acpp -c`, включая работу самой команды `acpp` |
| Линковка | Длительность отдельного вызова, который создаёт `.so` из `.o` и библиотек |
| Сборка целиком | Реальное ожидание завершения всех нужных компиляций и линковок, включая параллельные |
| Загрузка `.so` | Открытие библиотек, регистрация содержащихся в них ядер и поиск функций запуска |
| Первое исполнение | От начала запуска вычислений до их завершения; может включать второй этап компиляции, а не только работу GPU |
| Получение результата | Копирование результата с GPU на CPU и ожидание перед чтением |
| Повторное исполнение | Повтор уже подготовленного запроса, без отдельного копирования результата на CPU |
| Повтор целиком | Повтор до готового результата в памяти CPU, с копированием |
| Полный старт | От запуска приложения до первого готового результата; включает запуск и загрузку таблиц, в отличие от `summary` |

Названия функций загрузки в исходниках: `dlopen` открывает библиотеку, а `dlsym`
находит нужную функцию по имени. В измерениях они относятся к загрузке `.so`.

**Сумма времён параллельных команд не равна времени ожидания.** Условный пример:
если четыре команды одновременно работают по 100 мс, сумма равна 400 мс,
а ожидание может быть около 100 мс. Поэтому в таблицах отдельно показаны сумма
компиляций, сумма линковок и сборка целиком.

Команды измерялись встроенным `time` командной оболочки **Bash**. Он сохраняет:

- **`wall`** — сколько времени прошло по часам;
- **`user`** — процессорное время выполнения кода программы;
- **`system`** — процессорное время работы операционной системы от её имени.

`user + system` нельзя выдавать за `wall`, особенно при нескольких потоках.
Исходные файлы содержат секунды; в таблицах они переведены в миллисекунды.
Внутри C++ используются часы `std::chrono::steady_clock`, которые не зависят
от перевода системного времени. Ожидания GPU поставлены там, где нужно подтвердить
завершение работы или прочитать результат, а не после каждого ядра Q3.3.

Python только организует серии и затем обрабатывает сохранённые данные.
Он не используется как таймер или дополнительная обёртка компилятора внутри
измеряемого запроса. Правильность результатов проверяется после измерений.

Полный старт измеряет отдельная небольшая программа `first_result.cpp`:
она запускает приложение и ждёт сигнала «результат уже в памяти CPU».
Она же сохраняет, завершилось ли приложение нормально. Время последующих
повторов и закрытия приложения не называется временем первого ответа.

### 3.2. Какие уровни оптимизации сравнивали

Чтобы менять внутренние уровни без переустановки AdaptiveCpp, использовалась
отдельная тестовая библиотека `jit_control.cpp`. Она подменяет несколько
вызовов компилятора **только в исследуемом процессе** и записывает длительности.
Установленные файлы AdaptiveCpp не переписываются.
Библиотека подключается через **`LD_PRELOAD`** — настройку Linux, позволяющую
заранее загрузить дополнительную библиотеку в запускаемую программу.

В таблицах сохранены имена вариантов из исходных измерений:

| Имя варианта | Оптимизатор LLVM внутри AdaptiveCpp | Отдельный инструмент | Завершающая подготовка GPU-кода |
| --- | --- | --- | --- |
| `stock` | Штатный O3 | Штатный `opt` O3 | Штатные hipRTC/COMGR |
| `hiprtc33` | O3, с подключённым измерителем | `opt` O3 | hipRTC/COMGR без изменений |
| `hiprtc03` | O0 | `opt` O3 | hipRTC/COMGR без изменений |
| `hiprtc30` | O3 | `opt` O0 | hipRTC/COMGR без изменений |
| `hiprtc00` | O0 | `opt` O0 | **COMGR всё ещё оптимизирует код** |
| `clang33/03/30/00/11` | Уровень первой цифры | Clang с уровнем второй цифры | Вместо hipRTC используется другой, экспериментальный способ сборки через Clang |

Например, `hiprtc03` означает: внутренний оптимизатор поставлен на O0,
внешний `opt` оставлен на O3. Это **не** означает, что все оптимизации выключены.

`hiprtc00` тоже нельзя называть полностью неоптимизированным кодом: последний
оптимизатор COMGR остаётся. В `clang00` выбранные полные наборы оптимизаций
отключены, а Clang получает `-O0`; обязательные преобразования и встраивание
функций всё равно выполняются. Сырой промежуточный код на GPU не исполняет
ни один из вариантов.

Техническая деталь для воспроизведения: уровень LLVM O0 выбирается через
`buildO0DefaultPipeline`, то есть штатный набор преобразований для O0.
Это не удаление вообще всех преобразований компилятора.

### 3.3. Как проверяли работу после первого ответа

Для этого написан отдельный небольшой пример: он **отбирает строки по условию
и вычисляет выражение** для подходящих значений. Эти действия объединены в одном
ядре, без отдельного промежуточного результата для каждого действия.
Код проверки находится в `test/pcuda_jit_tiering/tiered.cpp`,
ядра — в `test/pcuda_jit_tiering/tier_kernel.cpp`, организация запусков —
в `test/pcuda_jit_tiering/tiered_run.py`.

Используются 64-битные целые числа около `2^53+1`, признаки наличия значения,
изменяемый порог отбора **`threshold`** и изменяемая прибавка **`offset`**.
Это позволяет проверить и изменение параметров, и сохранение точности:
`double`, 64-битный тип чисел с плавающей точкой, не может точно представить
все целые числа выше `2^53`.
Целочисленные значения в нём здесь не хранятся.

Основной пример содержит **65 539 строк** — число не кратно группе из
128 GPU-потоков, поэтому проверяется и неполная последняя группа.
Также есть случаи, когда не подходит ни одна строка.

В программе версии называются:

- **LOW** — базовый вариант, которым получаем первый результат;
- **HIGH** — последующий вариант, подготовленный со штатными оптимизациями O3
  через hipRTC/COMGR.

Последовательность проверки:

1. Загрузить исходные данные, начать измерение `summary`, подготовить память
   результата, собрать и загрузить LOW.
2. Выполнить LOW, включая его первую компиляцию для видеокарты, и скопировать
   результат на CPU. Отправить сигнал «ответ готов».
3. **После этого сигнала** запустить отдельный поток. Он снова вызывает
   `acpp -O0`, отдельно выполняет линковку и загружает HIGH, затем готовит
   его оптимизированный машинный код для GPU.
4. Чтобы вызвать подготовку HIGH, запустить один пустой блок с `count=0`.
   Блок — группа GPU-потоков. Он не читает и не меняет данные, но заставляет
   AdaptiveCpp подготовить исполняемый код. Адреса буферов, размер блока и
   существенные условия запуска совместимы с последующим обычным исполнением.
5. После готовности HIGH выполнить следующие запуски на нём. Уже запущенный
   LOW не переписывается. Для сравнения прототип затем измеряет обе готовые версии,
   а в режиме намеренного отказа фоновой задачи — только LOW.

Пустой блок из пункта 4 — **явная работа после ответа**, а не скрытая подготовка
до начала измерений первого запроса.

**Кеш готовых ядер** — хранилище уже подготовленных программ, позволяющее не
компилировать их повторно. Это не кеш результатов SQL: сами данные запроса
продолжают вычисляться заново.

Для LOW и HIGH сделаны разные имена C++-типов `FilterProject<0/1>` и разные
идентификаторы контейнеров кода. Контейнер называется **HCF — Heterogeneous
Container Format**, формат хранения кода для разнородных устройств;
AdaptiveCpp хранит в нём промежуточный код и сведения о ядре.
Разные идентификаторы нужны, чтобы кеш не принял HIGH за уже готовый LOW.
Просто изменить переменную с уровнем оптимизации недостаточно: при прежнем
[ключе кеша](https://github.com/AdaptiveCpp/AdaptiveCpp/blob/5989e1cfa4e70d55c65e786a4c71acb124ce54ff/include/hipSYCL/runtime/kernel_configuration.hpp)
среда выполнения может вернуть прежний код.

Это упрощение прототипа имеет цену: для HIGH повторно вызываются `acpp` и линкер.
В будущем можно было бы повторно использовать уже полученный промежуточный код
первого этапа, но здесь такой механизм не реализован.
Структура `TierArgs`, через которую передаются указатели и параметры, —
только тестовый формат, не утверждённый формат вызовов SQL-движка.

Проверялись два режима:

- **`idle` — без новых запросов:** после первого ответа фоновая подготовка
  заканчивается, затем измеряются повторные исполнения LOW и HIGH.
- **`overlap` — с новым запросом во время подготовки:** стенд ждёт, когда
  фоновый поток войдёт во внутренний оптимизатор LLVM, и именно тогда вызывает
  уже готовый LOW. Так проверяется, будет ли фон мешать следующему запросу.

Работа с данными упорядочена через **stream** — очередь команд GPU, в которой
зависимые копирования и вычисления выполняются в нужном порядке.
Для независимой подготовки пустого HIGH используется отдельная очередь.
Перед освобождением памяти или выгрузкой кода проверяется завершение работы;
фоновый поток также должен закончить работу раньше освобождения его ресурсов.

Владение памятью, очередями и библиотеками оформлено через **RAII — Resource
Acquisition Is Initialization**: C++-объект владеет ресурсом и освобождает его
при завершении своего времени жизни. Это не отменяет необходимости сначала
дождаться использующих ресурс операций.

### 3.4. Повторения, кеши и диагностические записи

**Первый запуск**, который в исходных данных называется **`cold`**, выполнялся
в новом процессе с новым, до этого отсутствовавшим каталогом кеша AdaptiveCpp.
**Повторный запуск**, или **`warm`**, выполнялся в том же процессе после первого,
с сохранением готового кода.

Каталог задаёт `ACPP_APPDB_DIR`. Кеши операционной системы, HIP и драйвера
отдельно не очищались. Поэтому новый кеш AdaptiveCpp **не означает**, что пусты
все остальные кеши компьютера.
Файлы `.so` сохраняются среди результатов для воспроизведения, но не используются
как постоянный кеш SQL-модулей между запусками приложения.

Для Q3.3 использовались следующие серии:

- Предварительное сравнение настроек, ранее названное *screening*: по три новых
  процесса на вариант и режим диагностики, по девять вычислений в каждом.
- Подтверждающее сравнение: по **семь новых процессов** на вариант и режим,
  в каждом первое вычисление и **восемь повторов**.
- Порядок вариантов циклически менялся. Режимы с диагностикой и без неё также
  чередовались, чтобы не отдавать одному варианту постоянно более выгодный порядок.
- Частоты и температуры не фиксировались; фоновые нагрузки рабочего стола
  могли влиять на время. Небольшое отличие само по себе не доказывает ускорение.

**Трасса**, или **trace**, — диагностический файл с длительностями отдельных
операций компилятора. Сохранялись трассы Clang с `-ftime-trace` и линкера LLD
с `--time-trace` для первого этапа сборки. Проводились сопоставимые серии
с этими записями и без них: запись тоже может занимать время.
В именах запусков эти режимы называются **`trace` — с трассами** и
**`plain` — без трасс**.

Второй этап измерялся напрямую, а не вычитанием времени повторного запроса
из первого. Для чтения подробных таблиц полезны имена записанных операций:

| Имя в файле измерений | Простое объяснение |
| --- | --- |
| `fullTransformation` | Всё преобразование промежуточного кода в готовый код выбранного способа сборки |
| `optimizer` | Работа внутреннего оптимизатора LLVM в AdaptiveCpp |
| `external_tool` | Запуск отдельного `opt` или Clang и ожидание его завершения |
| `hiprtcLinkComplete` / `hiprtc_complete` | Завершающая работа hipRTC, включающая создание и связывание машинного кода |

Три последние операции находятся **внутри** `fullTransformation`.
Их нельзя снова прибавлять к его времени. Время отдельного инструмента,
измеренное Bash, и C++-интервал вокруг его запуска имеют разные границы.
Неизмеренный остаток не объявляется «чистым временем драйвера».

Данные сохраняются в **JSON — JavaScript Object Notation**, текстовом формате
для структурированных записей. Имена полей и исходные результаты в этих файлах
при переписывании отчёта не менялись.

## 4. Что получилось в измерениях

Во всех таблицах время дано в **миллисекундах**. Показана **медиана** — середина
упорядоченного ряда наблюдений, а не лучший запуск. Запись `[min; max]`
содержит минимальное и максимальное наблюдение. Это не гарантированные пределы
будущих запусков и не доверительный интервал.

У каждой колонки своя медиана. **Медианы разных колонок нельзя складывать,
чтобы получить медиану общего времени.** Само общее время измерено отдельно.

### 4.4. Почему фон задерживает следующий запрос — и при чём здесь мьютекс

Вернёмся к слову **«незаметно»** из исходного вопроса. Если пользователь получил
ответ и больше ничего не запускает, компиляцию действительно можно выполнить
в образовавшейся паузе. Но он может сразу отправить следующий запрос.

Ожидаемое поведение: пока улучшенный код ещё не готов, новый запрос исполняется
на уже готовом базовом коде и **не ждёт улучшения**. Именно это проверял режим
`overlap`, а не только способность создать фоновый поток.

Ниже результаты небольшого примера на **65 539 строках**, не Q3.3.
Показаны серии без трасс. Длительности посчитаны по успешным процессам;
колонка «процессы» не даёт забыть об аварийном завершении одного из запусков.

| Базовый вариант / режим | Успешные процессы | **summary [min; max]** | Вся фоновая подготовка [min; max] | Повтор LOW целиком | Повтор HIGH целиком | Вызов LOW во время JIT [min; max] |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| hiprtc00 / idle | 7/7 | **228,983 [225,386; 246,407]** | 239,173 [235,700; 243,856] | 0,128 | 0,125 | Нет запроса |
| hiprtc00 / overlap | 7/7 | **229,634 [225,354; 246,817]** | 238,390 [232,069; 255,522] | 0,125 | 0,125 | 34,611 [34,018; 35,737] |
| clang00 / idle | 7/7 | **314,638 [308,129; 320,057]** | 239,044 [234,976; 241,563] | 0,558 | 0,124 | Нет запроса |
| clang00 / overlap | **6/7** | **319,185 [313,412; 328,261]** | 237,952 [235,509; 240,382] | 0,558 | 0,122 | 35,988 [35,486; 37,189] |

**Что видно:** у `hiprtc00 / overlap` обычный повтор LOW занимает **0,125 мс**,
а вызов того же уже готового LOW во время фоновой компиляции — **34,611 мс**.
Новый запрос задержался не потому, что для него ещё не было кода.

**Объяснение по исходникам AdaptiveCpp:** доступ к общему кешу готовых ядер
защищён **мьютексом** — механизмом, который разрешает работать с защищёнными
данными только одному потоку за раз. Он нужен, чтобы потоки не испортили общие
данные одновременными изменениями. Однако здесь он удерживается надолго —
пока создаётся новый исполняемый код.

В результате получается такая последовательность:

```text
Фоновый поток:  занял общий доступ к кешу → компилирует HIGH → освободил доступ
Новый запрос:                хочет получить готовый LOW → ждёт → исполняет LOW
```

Это **не блокировка таблиц базы данных** и не новая возможность, которую мы
добавили. Это уже существующая внутренняя организация AdaptiveCpp.
Технические места, в которых она видна:

- [`get_or_construct_jit_code_object`](https://github.com/AdaptiveCpp/AdaptiveCpp/blob/5989e1cfa4e70d55c65e786a4c71acb124ce54ff/include/hipSYCL/runtime/kernel_cache.hpp#L312-L350)
  удерживает общий `kernel_cache::_mutex` при компиляции и создании исполняемого объекта;
- [проверка уже готового объекта](https://github.com/AdaptiveCpp/AdaptiveCpp/blob/5989e1cfa4e70d55c65e786a4c71acb124ce54ff/src/runtime/kernel_cache.cpp#L599-L608)
  также берёт этот мьютекс.

**Поэтому мьютекс появился в исследовании:** нужно было проверить не только
«можно ли скомпилировать после ответа», но и «не перенесём ли мы ожидание
на следующий запрос». Проверка показала, что такая опасность реальна.
Переместить работу в поток недостаточно; долгую компиляцию нужно отделить
от краткого доступа к уже готовым ядрам.

Успешные запуски также подтвердили переключение версии. Счётчик показывает
**одну компиляцию для устройства до первого ответа и две суммарно после подготовки
HIGH**. Восемь следующих смен порога и прибавки не создают новых компиляций.
Это проверка счётчиком, а не предположение на основании маленького времени.

У `hiprtc00` HIGH почти не ускоряет вычисления: завершающий COMGR и так
оптимизировал LOW. У `clang00` HIGH ускоряет следующие исполнения, но первый
ответ и подготовка нового кода остаются дорогими.

### 4.5. Почему отдельно проверяли завершение приложения

Компиляция после ответа не должна оставлять приложение в состоянии, в котором
оно потом аварийно завершится. Поэтому проверялся не только первый результат,
но и нормальное завершение процесса.

В первоначальной серии упали четыре запуска:
`s0-clang00-overlap-trace`, `s3-clang00-overlap-plain`,
`s5-clang00-idle-trace`, `s6-clang00-idle-trace`.

**SIGSEGV** — сигнал Linux о недопустимом обращении к памяти; его номер — **11**.
Программа наблюдения записала: сигнал 11, результат до этого уже был готов
(`CPU-ready=true`), но процесс завершился неуспешно.

Для разбора сохранён **core dump** — снимок состояния аварийного процесса,
включая память и состояния потоков. В снимке процесса с номером **37362** видно:

- основной поток уже закрывал служебные библиотеки — находился внутри
  `exit`, `__cxa_finalize` и кода завершения hipRTC;
- служебный поток пытался исполнять код по адресу, не связанному ни с одним
  из текущих отображений файлов библиотек в памяти;
- файлы результатов и событий компиляции успели записаться, но нормального
  завершения не произошло.

**Подтверждённый факт:** ошибка произошла при завершении процесса.
**Вероятное объяснение:** проблема времени жизни служебных библиотек или их
потоков при сочетании двух способов компиляции, Clang и hipRTC.
Это **не доказательство ошибки вычислений с O0**. Точная ошибка в коде библиотек
и владелец аварийного адреса не установлены.

Проверен отдельный диагностический обход: **`--pin-driver PATH`**, где `PATH` —
путь к библиотеке AMD. Программа загружает её с `RTLD_NODELETE`, то есть запрещает
обычную выгрузку её кода из памяти при закрытии ссылки на библиотеку.
Держатель ссылки при этом освобождается автоматически; ожидания GPU и обычное
завершение приложения сохранены. Немедленный выход без выполнения очистки
через `_Exit` не используется, установленные библиотеки не меняются.

Результат отдельной серии с удержанием библиотеки:

| Базовый вариант / режим | Процессы без трасс + с трассами | **summary без трасс [min; max]** | Фон без трасс | Повторы LOW/HIGH целиком | LOW во время JIT |
| --- | ---: | ---: | ---: | ---: | ---: |
| clang00 / idle | 7/7 + 7/7 | **361,285 [351,676; 367,124]** | 265,853 | 0,550 / 0,112 | Нет запроса |
| clang00 / overlap | 7/7 + 7/7 | **359,554 [343,586; 363,494]** | 276,227 | 0,551 / 0,108 | 39,311 [38,226; 47,751] |

С трассами `summary` соответственно **357,245 / 359,746 мс**, задержанный вызов
LOW — **38,554 мс**. Все **28/28** процессов нормально завершились и прошли
проверку результатов.

Это подтверждение работоспособности обхода **в данной ограниченной проверке**,
не доказательство универсального исправления ROCm. Серия проведена позднее
и с другой подготовкой библиотек при запуске. Её нельзя объединять с прежней
или объяснять всё отличие времени только удержанием библиотеки.
Четыре прежних падения остаются неуспешными результатами.
Автоматически переносить такой специфичный для AMD обход в движок не предлагается.

Также проверен намеренный отказ фоновой задачи: команда сборки возвращала
код ошибки **17**. Получено **12/12** успешных проверок того, что LOW продолжает
работать, HIGH не используется и второй компиляции для устройства нет.
Это тест обработки отказа задачи, не настоящая ошибка оптимизатора и не серия
для выводов о скорости.
В обычных режимах неожиданная ошибка фоновой задачи завершает эксперимент
с ошибкой. Проверка намеренного отказа не означает, что прототип уже умеет
продолжать обслуживание запросов после любой ошибки компилятора.

## 5. Насколько можно доверять результатам

### 5.1. Проверка вычислений

- Две основные серии Q3.3: **144 процесса и 1296/1296 совпадений** с независимым
  ручным эталоном `test/queries/result/scale10/33.txt`.
  При сравнении не важна перестановка строк, но важно количество одинаковых
  строк: программа не может незаметно потерять или продублировать результат.
- Все успешные запуски небольшого примера, включая пробные, проверку отказа,
  удержание библиотеки и последнюю проверку инструментов: **1600 результатов
  и 108 849 748 поэлементных проверок**. Независимая программа на Python
  вычисляла ожидаемые значения по номеру строки, не вызывая GPU-помощники
  проверяемой реализации.
- Проверены большие 64-битные целые, признаки отсутствующих значений, отсутствие
  подходящих строк, знаковая прибавка, неполный последний блок и изменение
  параметров между запусками.
- **Четыре аварийных процесса основной серии не включены как успешные проверки**,
  даже если какие-то файлы результатов успели появиться.

Проверка правильности выполнялась после измеряемых запусков. Её время
не включено в `summary`; сама проверка не выполнялась параллельно серии измерений.

### 5.2. Проверка сборки, повторного использования и учёта времени

- У LOW и HIGH по одному ядру и разные идентификаторы HCF. У Q3.3 — четыре
  независимых идентификатора. Списки включённых заголовков не содержат
  `sycl/sycl.hpp`: новые PCUDA-примеры не подтягивают полный SYCL-заголовок.
- В коде проверяются допустимые размеры, размеры блоков и переполнения до
  выделения памяти и запуска ядра. Не использовались настройки `fast-math`,
  которые разрешают ослаблять точность вычислений ради скорости.
- Для Q3.3 записаны четыре вызова компиляции, четыре вызова линковки,
  один сценарий сборки и четыре загрузки. В вариантах с внутренним наблюдением
  — ровно четыре компиляции для устройства при первом исполнении, без новых
  при повторах. В примере с LOW/HIGH их две при успешной подготовке и одна
  при отказе фоновой задачи.
- Проверки в C++ работают и в оптимизированной сборке: они используют исключения
  и коды ошибок, а не отключаемый через `NDEBUG` механизм `assert`.
- Дополнительная проверка файлов подтвердила контрольные суммы измеренных
  исходников и тестовой библиотеки, идентификаторы ядер, списки заголовков,
  ожидаемые счётчики и включение подготовки памяти в `summary`.
  Сумма неперекрывающихся составляющих проверяет охват общего таймера,
  но не заменяет его.
- В ходе исследования прошли **шесть новых проверок инструментов на CPU**
  и **11 существующих проверок этапа 0**. Они проверяют независимый расчёт,
  точность больших целых, размер результата, сценарии сборки, раздельный выбор
  уровней оптимизации и правильное чтение вложенных записей времени.
  Проверены синтаксис **шести Python и 394 Bash-файлов**, ссылки и пробелы
  в изменённых файлах. Это исторические проверки исследования 31 октября,
  а не новые GPU-испытания при редактуре этого документа.

### 5.3. Неудачные попытки не удалены

Сохранены и ошибки подготовки измерителя:

- В первой команде создания PCH не хватало `-c`, поэтому заголовок не собрался.
- При ошибочной передаче `LD_PRELOAD` дочернему `opt` внутрь компилятора
  попадала ещё одна библиотека LLVM. Одни и те же настройки регистрировались
  повторно, и процесс принудительно завершался с **SIGABRT** — сигналом
  аварийного прерывания программы.
- Это исправлено подготовкой отдельного набора переменных окружения для
  дочернего процесса, без изменения общих настроек уже работающих потоков.
- После основных измерений сценарий запуска также научен возвращать ошибку,
  если в отчёте указано `report.success=false`, и завершать свою группу
  процессов при превышении допустимого времени ожидания.
  Исходные статусы старых запусков от этого не менялись.

Эти неудачные попытки не используются как доказательство ускорения.
Их файлы и ограничения воспроизводимости перечислены в разделе 7.

### 5.4. Что остаётся непроверенным

Не выполнялась новая полная проверка SQL-движка через `db_cli`, всех 13 запросов
SSB и действующих категорий из `olap_bench/manifest.json` — перечня проверяемых
возможностей проекта. Не проверены при новых настройках компилятора объединения
таблиц и коллективные операции GPU, например совместное суммирование и
вычисление накопленных сумм.

Также не проверена полная семантика **SQL NULL**, то есть отсутствующего значения,
и **3VL — Three-Valued Logic**, трёхзначная логика SQL: «истина», «ложь»,
«неизвестно». Признак отсутствующего значения в маленьком примере не заменяет
проверки всей этой семантики и набора `test/nullable_data`.

Отмена длительной фоновой компиляции, работа многих пользователей одновременно
и другие видеокарты также остаются за границами проверки.
Движок не менялся, поэтому `test/test_optimizer.cpp` и поля времени SQL-запросов
в этом исследовании не изменялись. Без будущих проверок на реальном движке
новую политику нельзя считать готовой для SQL.

## 6. Как это связано с Android и что делать дальше

### 6.1. Почему пример Android похож, но не является готовым решением для нас

В Android есть **ART — Android Runtime**, среда выполнения приложений.
Она может исполнить метод несколькими способами:

- **Интерпретатором** — заранее написанной программой, которая читает команды
  приложения и выполняет их, не создавая отдельный машинный код для каждого
  метода перед его первым выполнением.
- Кодом, скомпилированным во время работы, то есть через JIT.
- Кодом, подготовленным заранее — **AOT, Ahead-Of-Time compilation**.

Поэтому Android может продолжать работу до появления улучшенного кода:
**у него уже есть начальный способ исполнения**. Затем можно собрать сведения
об использовании приложения и подготовить более удачный вариант.
Фоновая компиляция `dex2oat` — так называется соответствующий инструмент Android —
не означает, что процессор умеет выполнять ещё не скомпилированные GPU-инструкции.
Описание механизма: [документация ART](https://source.android.com/docs/core/runtime/jit-compiler).

**PGO — Profile-Guided Optimization**, оптимизация по профилю выполнения,
отвечает на другой вопрос: **какие оптимизации стоит применять?**
Профиль содержит сведения о реальной работе программы, например какие участки
выполняются чаще. Компилятор использует их при подготовке кода.
PGO само по себе не создаёт фоновый поток и не организует замену исполняемой версии.
[Описание PGO в Clang](https://releases.llvm.org/17.0.1/tools/clang/docs/UsersManual.html#profile-guided-optimization).
В нашем прототипе сбор такого профиля **не включался**.

Для различения близких идей:

| Подход | Что именно откладывается или переносится | Чего он сам по себе не делает |
| --- | --- | --- |
| Ленивая компиляция, *lazy compilation* | Компиляция начинается только при первом обращении к коду | Первый вызов всё равно ждёт, если готового исполнителя нет |
| Многоуровневая компиляция, *tiered compilation* | Более дорогая оптимизация выполняется после подготовки базового варианта | Не гарантирует, что базовый вариант достаточно дёшев и фон никому не мешает |
| PGO | При выборе оптимизаций учитываются сведения о прошлых исполнениях | Не заменяет базовый исполнитель и управление версиями |
| AOT | Машинный код готовится до запуска приложения | Не даёт автоматически готовый код для ещё неизвестного SQL-запроса |
| Предположительная компиляция, *speculative compilation* | Вероятно нужный код подготавливается заранее | Может зря тратить ресурсы, если предположение о будущем запросе неверно |

В LLVM есть **ORC — On-Request Compilation**, набор компонентов для создания
собственного JIT-компилятора. Он поддерживает параллельную подготовку кода,
отложенную компиляцию при обращении и управление временем жизни готовых версий:
[документация LLVM 17](https://github.com/llvm/llvm-project/blob/llvmorg-17.0.0/llvm/docs/ORCv2.rst),
[пример предположительной компиляции](https://github.com/llvm/llvm-project/blob/llvmorg-17.0.0/llvm/examples/SpeculativeJIT/SpeculativeJIT.cpp).

Но это строительные элементы для разработчика, не переключатель AdaptiveCpp.
Первый вызов, отложенный через такой механизм, всё равно должен дождаться кода.
Пример, который вызывает готовые CPU-функции по адресам в памяти, нельзя
автоматически считать готовым способом загрузки и запуска AMD GPU-ядра.
ORC в движок или прототип не добавлялся.

### 6.2. Какие варианты решения остаются реалистичными

**1. Оставить только `acpp -O0`.**
Это уже делалось на первом этапе компиляции. После него в библиотеке лежит
промежуточный код, который ещё надо подготовить для видеокарты при первом
исполнении. Поэтому этот параметр не убирает интересующее нас ожидание.

**2. Уменьшить оптимизации, которые выполняются непосредственно перед запуском.**
Это проверено. Отключение двух промежуточных наборов оптимизаций уменьшило
часть работы, но завершающая сборка и оптимизация COMGR остались.
Изменение требует доступа к внутреннему устройству компилятора;
обычного документированного параметра для проверенной схемы не найдено.
Выгода всего готового прототипа относительно штатного запуска не подтверждена.

**3. Получать первый машинный код с минимальной оптимизацией, затем улучшать его.**
Именно такой вариант проверен через Clang O0. На Q3.3 он ухудшил и первый
ответ, и повторные вычисления. Значит, его нельзя рекомендовать как
универсальный быстрый начальный вариант. Это не доказательство бесполезности
всех возможных быстрых компиляторов, только результат проверенного способа.

**4. Готовить улучшенную версию после ответа.**
Механизм проверен и работает. Но сейчас фоновая компиляция занимает общий
доступ к кешу и заставляет следующий запрос ждать даже готовый код.
Нужна переработка этой части среды выполнения, а не только дополнительный поток.

**5. Иметь заранее готовые универсальные GPU-операции или интерпретатор плана.**
Тогда после нового SQL-запроса можно было бы передать готовому исполнителю
описание действий и параметры, а специализированное ядро готовить позднее.
В этом варианте начальный исполнитель, как интерпретатор в Android, уже существует.
Он тоже когда-то должен получить машинный код — например при установке или запуске
базы. Эту стоимость нужно показывать отдельно, а не объявлять исчезнувшей.
Исполнитель произвольного SQL в данном исследовании **не реализован**.
Просто заранее прогреть известные служебные ядра полезно, но это ещё не такой
универсальный исполнитель нового плана.

**6. Первый запрос выполнять на CPU.**
Теоретически это ещё один начальный исполнитель, но нужен самостоятельный
корректный код запроса и учёт передачи данных. Если таблицы уже на GPU,
копирование на CPU может перечеркнуть выигрыш. Этот путь не добавлялся и не
предлагается как незаметная замена согласованному выполнению на видеокарте.

**7. Заранее собирать код для конкретного производителя или перейти на другую
систему компиляции и выполнения GPU-программ.**
Это меняет выбранную архитектуру и требует отдельной проверки переносимости.
Такой переход не выполнялся и не предлагается как незаметная замена
согласованному пути через generic PCUDA.

**8. Сохранять готовые SQL-модули между запусками приложения.**
Это противоречит текущему ограничению проекта: кеш SQL-модулей нужен только
внутри процесса. Постоянный кеш таких модулей не добавлялся.
Собственный кеш машинного кода AdaptiveCpp — отдельный механизм, состояние
которого в измерениях всегда оговаривается.

Для первого ответа важно сравнивать **всю сумму ожидания**, а не только
компиляцию. Если базовый код быстрее подготовить, но он намного дольше считает,
пользователь может получить ответ позже.
Фоновая подготовка улучшает только **будущие** исполнения. Она потребляет
процессор, память и энергию и может не окупиться для одноразового запроса.
Из одного небольшого примера здесь не устанавливаются новые требования к скорости.

### 6.3. Что пришлось бы изменить при дальнейшем внедрении

Ниже — **предложения**, а не уже согласованные или выполненные изменения:

1. **Разделить подготовку кода и владение данными запроса.** Памятью, очередями,
   планом и версиями модулей должен управлять исполнитель запроса.
   Компилятору нужно передавать неизменяемое описание работы,
   а не общий изменяемый `ExecutionContext`.
2. **Хранить уровень подготовки в идентификаторе версии кода.** Для каждой версии
   компилятор должен получать этот уровень явно. Нужно сохранять и описание
   её аргументов. Оптимизатор может удалить
   неиспользуемые аргументы по-разному в разных версиях; нельзя передавать
   параметры по схеме от другого варианта.
   Это часть будущего **ABI — Application Binary Interface**, правил вызова
   скомпилированного модуля и размещения передаваемых данных. SQL ABI ещё не утверждён.
3. **Не держать общий мьютекс во время долгой компиляции.** Доступ к готовому LOW
   должен занимать короткое время, пока HIGH готовится независимо.
   Отдельно нужно не допускать двух одновременных сборок одной и той же версии.
4. **Сделать отдельные функции подготовки кода без фиктивного запуска ядра.**
   Это будущий **API — Application Programming Interface**, набор функций,
   которым мог бы пользоваться исполнитель. Нельзя без защиты делить между
   потоками изменяемые настройки очереди `_config` и механизм подготовки аргументов.
5. **Заменять версию только для будущих запусков.** Старый код и его аргументы
   нельзя освобождать, пока ими пользуются уже запущенные операции.
   При ошибке фона нужно оставить рабочий LOW. Проверять следует и служебные
   потоки HIP/HSA, а не только завершение наших GPU-вычислений.
6. **Ограничить стоимость фона.** Нужны ограничения на число задач, память,
   число версий и правила остановки при завершении сеанса.
   Один поток сам по себе не доказывает, что пользовательские запросы не пострадают.
7. **Не встраивать обычные значения SQL-параметров в HIGH.** Новый порог отбора
   или признак NULL должен передаваться как данные, если тип совместим.
   Согласованное ограничение — до восьми версий для разных схем типов и один
   универсальный резервный вариант — автоматически не расширяется из-за
   появления уровней оптимизации.
8. **Проверить уже реальный SQL-движок.** Нужны `db_cli`, все 13 SSB, действующие
   проверки из перечня проекта, независимая проверка NULL и трёхзначной логики,
   затем отдельное согласование времени полного SQL-запроса.

**Рекомендация по результатам исследования:** не включать Clang O0 или
безусловную фоновую компиляцию в основной путь переноса движка.
Продолжать согласованные этапы 1–8. Если будет отдельно выбран следующий
эксперимент, наиболее содержательные направления — дешёвый универсальный
начальный GPU-исполнитель либо подготовка специализированного кода без
длительной общей блокировки. Выбор и объём требуют решения пользователя.

## 7. Как воспроизвести проверку и где лежат доказательства

### 7.1. Сборка тестового инструмента

Команды выполняются из корня проекта. Это отдельная CMake-сборка по
`test/pcuda_jit_tiering/CMakeLists.txt`, не изменение основной сборки движка.
**CMake** — система подготовки правил сборки программы.

```bash
LLVM=/opt/rocm_sdk_612
ACPP=/opt/AdaptiveCpp
ROCM=/opt/rocm_sdk_612
GCC_FLAG=--gcc-install-dir=/usr/lib/gcc/x86_64-pc-linux-gnu/14.3.1
WORK=$(mktemp -d "$PWD/build/pcuda-jit-reproduce-XXXXXXXX")
cmake -S test/pcuda_jit_tiering -B "$WORK/control" \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER="$LLVM/bin/clang++" \
  -DCMAKE_CXX_FLAGS="$GCC_FLAG" -DLLVM_DIR="$LLVM/lib/cmake/llvm" \
  -DACPP_PREFIX="$ACPP" -DROCM_PREFIX="$ROCM"
cmake --build "$WORK/control" -j 2
```

Это примеры путей проверенного компьютера: для другого компьютера их нужно
заменить. Они не записаны в код движка как обязательные пути.
Тестовая подмена рассчитана на Linux и LLVM 17; совместимость с другой сборкой
AdaptiveCpp требует отдельной проверки.

### 7.2. Измерение Q3.3

`test/pcuda_jit_tiering/run.py` — программа организации подтверждающей серии:

```bash
python3 test/pcuda_jit_tiering/run.py \
  --control "$WORK/control/libjit_control.so" --data data/10 \
  --extra-flag="$GCC_FLAG" --series 7 --runs 9 --diagnostics both \
  --variants stock,hiprtc33,hiprtc03,hiprtc30,hiprtc00,clang00
```

`--series 7` означает семь новых запусков программы для каждой настройки
и режима диагностики, `--runs 9` — первое вычисление и восемь повторов.
`--diagnostics both` включает отдельные серии с трассами и без них.
Для предварительного сравнения использовалось `--series 3`, а в список
добавлялись `clang33,clang03,clang30,clang11`.

По умолчанию выбирается видеокарта с `780M` в имени; это можно изменить
параметром `--device-name`. Каждый запуск организатора создаёт свой каталог
и сохраняет копии исходников и тестовой библиотеки.

### 7.3. Проверка фоновой подготовки и отказа задачи

`test/pcuda_jit_tiering/tiered_run.py` — программа организации проверки LOW/HIGH:

```bash
python3 test/pcuda_jit_tiering/tiered_run.py \
  --control "$WORK/control/libjit_control.so" --extra-flag="$GCC_FLAG" \
  --low-profiles hiprtc00,clang00 --modes idle,overlap \
  --series 7 --runs 8 --rows 65539 --diagnostics both
```

Здесь `--runs 8` означает восемь последующих повторов каждого доступного
варианта после первого результата. Режимы `idle` и `overlap` описаны в разделе 3.3.
Для проверки намеренного отказа задачи: `--modes failure --series 3`.

Отдельная проверка удержания библиотеки использует `--low-profiles clang00`
и **явный** `--pin-driver "$ROCM/lib/libamdhip64.so"`, остальные параметры те же.
Без этого параметра удержание не включается. Оно не считается универсальным
исправлением среды выполнения.

### 7.4. Обработка и проверка уже сохранённых данных

Следующие инструменты запускаются **после завершения всех измеряемых процессов**:

```bash
python3 test/pcuda_jit_tiering/inventory.py \
  --acpp-source /home/aidar/AdaptiveCpp --acpp-prefix "$ACPP" \
  --llvm-prefix "$LLVM" --control-build "$WORK/control"
python3 test/pcuda_jit_tiering/analyze.py build/pcuda-jit-tiering/q33-jgw97j6a/report.json
python3 test/pcuda_jit_tiering/audit.py \
  build/pcuda-jit-tiering/q33-jgw97j6a/report.json --data data/10
PYTHONDONTWRITEBYTECODE=1 python3 test/pcuda_jit_tiering/test_tools.py
```

- `inventory.py` записывает версии, настройки, исходники и контрольные суммы.
- `analyze.py` вычисляет статистику по законченным измерениям.
- `audit.py` проверяет файлы, их идентичность, счётчики и команды сборки.
- `test_tools.py` проверяет работу самих вспомогательных инструментов.

Для новых измерений нужно подставить новые пути `report.json`.
`analyze.py` и `audit.py` могут принимать несколько таких файлов.
Полная выгрузка исследования содержит семь измерительных наборов:
две Q3.3-серии и пять серий небольшого примера из следующей таблицы.
Инструменты создают новые каталоги и не переписывают старый признак успеха `success`.
Исходные поля времени SQL-движка не переопределены; границы новых измерений
описаны также в [timing.md](../../timing.md#jit-tier-timing).

### 7.6. Что остаётся открытым

Не реализованы быстрый универсальный начальный исполнитель, отдельные функции
подготовки GPU-кода и использование новых версий без долгой общей блокировки.
Не установлена точная причина ошибки при завершении служебных библиотек AMD
и не получено поддерживаемое авторами исправление. Не проверены выигрыш
на полном SQL-движке и другие устройства.

**Переписывание отчёта не закрывает эти вопросы, не меняет результаты
измерений и не является поручением автоматически внедрять следующую часть проекта.**
