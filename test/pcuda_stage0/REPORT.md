### Архив A. Этап 0: модули PCUDA, GPU-примитивы и baseline

Изолированный технический стенд, **не новый SQL runtime и не утверждённый ABI**.
PCUDA-часть не использует заголовки движка, SQL parser, `sycl/sycl.hpp`, default stream,
chevron launch или межмодульные device-вызовы. Основная сборка не меняется.
Дополнительный `sql_baseline.py` наблюдает существующий SYCL-путь через `db_cli`.

#### Запуск

Из корня проекта (Python 3, Bash 5.3, AdaptiveCpp с PCUDA, lld, `nm`, `ldd`):

```bash
python3 test/pcuda_stage0/run.py --device-name 780M \
  --extra-flag=--gcc-install-dir=/usr/lib/gcc/x86_64-pc-linux-gnu/14.3.1
```

`780M` и путь GCC — параметры конкретного проверенного окружения, не требования
к движку. Для другого окружения задайте подстроку имени устройства и совместимый
GCC; `--acpp` выбирает драйвер, `--extra-flag` можно повторять. Без подходящего
устройства стенд завершается ошибкой, а не переключается молча на CPU.
По умолчанию запускаются обе PCUDA-части; `--suite modules` оставляет только
проверку двух модулей, `--suite collectives` — reduction/scan и атомики.

Каждый запуск создаёт собственный каталог `build/pcuda-stage0/run-*`;
`--output-root` меняет родительский каталог. В нём остаются все команды и wall
times (`report.json`), stdout/stderr, зависимости заголовков, PCH, объекты,
библиотеки, списки символов и изолированные каталоги device JIT. Артефакты
сохраняются для анализа и не переиспользуются как постоянный кеш SQL-модулей.
Пути toolchain в исходниках не зашиты. Исходники и runtime-библиотеки записываются
в отчёт с SHA-256. `success: true` появляется только после всех проверок.
Текущие измерения команд выполняет нативный Bash `time`; Python организует
запуски и offline-анализ Clang/lld traces. Первые исторические результаты ниже
сохранены без переписывания, их методика отличалась.

#### Проверки модульной части

- Два отдельных `.cpp` → два объекта → две отдельные `.so`. Каждая содержит одно
  `pcudaParallelFor` и свою host-обёртку; общей перелинковки нет.
- Обе библиотеки экспортируют `launch_probe`, но используют разные namespace
  для тел ядер. `RTLD_LOCAL` и `dlsym` конкретного handle различают точки входа.
- Для проверенной версии AdaptiveCpp извлекаются HCF object-id и имена ядер;
  проверяется по одному ядру на модуль, разные имена двух ядер и уникальность ID
  восьми собранных модулей этой части (28 в полном стенде). Это диагностика текущего формата, не публичный API
  загрузчика движка; при изменении формата стенд явно завершится ошибкой.
- Один явный stream: memset → H2D → прибавление параметра в первом модуле →
  преобразование `x * 3 + 7` во втором → D2H → ожидание перед чтением CPU.
  Между ядрами нет ожидания или host-материализации.
- Буферы GPU, pinned host-память, stream и `dlopen` handles имеют RAII-владение.
  Перед освобождением/выгрузкой выполняется проверяемое ожидание. Если ожидание
  при teardown не удалось, процесс аварийно завершается без небезопасного free.
- Три цикла загрузки/выгрузки с чередованием порядка загрузки. В конце каждого
  цикла дополнительно ставится работа и копирование без явного ожидания:
  завершение обеспечивает деструктор модуля до `dlclose`; результат проверяется.
- На вариант: 72 проверки результатов, включая пустой вход, 1/127/128/129
  элементов, 100003 элемента, три значения независимого параметра, повторное
  использование буферов и определённую модульную арифметику `uint32_t`.
  Дополнительно три проверки результата после выгрузки с поставленной работой.
  Это не тест знаковой SQL-арифметики и не решение по SQL-типам.
- До аллокаций проверяются размеры, до запуска — пределы устройства и сетки.
  Нулевой block/default stream отклоняются. Проверки не используют `assert` и
  не отключаются через `NDEBUG`.
- Матрица `-O0`/`-O3` × PCH/без PCH. PCH создаётся отдельно с совместимыми
  флагами, проверяется Clang magic `CPCH`, затем реально используется через
  `-include-pch`. Dependency files проверяются на отсутствие полного SYCL API;
  внутренние libkernel-заголовки самой PCUDA допустимы.

Compile — wall time отдельного вызова `acpp -c`, включая работу драйвера;
link — wall time отдельного `acpp -shared` над объектом. Это не измерения чистого
frontend/backend. Load включает `dlopen`, регистрацию HCF, `dlsym` двух модулей.
Выполнение включает memset, копирования, два запуска и ожидание результата,
но исключает CPU-сверку. Первое выполнение включает наблюдаемый device JIT;
его собственное время отдельно не выделено. Warm — медиана следующих восьми
выполнений на 100003 элементах с разными значениями параметра в первом цикле.

Каждый вариант работает в новом процессе со своим первоначально пустым
`ACPP_APPDB_DIR`; внутренний кеш процесса сохраняется при повторных запусках и
перезагрузках модулей. OS/filesystem caches не очищались. Порядок вариантов
фиксирован, статистики нескольких независимых серий нет: таблица не доказывает
преимущество O0/O3 и не задаёт SLA. Простые ядра не представляют сложность SSB.

#### Публичный API и оставшаяся работа этапа 0

На устройстве проверены перечисление backend/platform/device, свойства
устройства, явный stream, malloc/free, pinned host allocation, async memcpy и
memset, `pcudaParallelFor`, синхронизация и диагностика ошибок.

иерархический exclusive scan, а также требуемые 32-/64-битные PCUDA-атомики.
Готовый публичный reduction/scan API не требуется: реализация использует только
PCUDA и барьеры всех потоков, без subgroup/warp-предположений. Код остаётся
экспериментальным, не интегрирован в движок и не закрывает этап 4 миграции.

Расширенные проверки, команды SQL baseline и обнаруженное расхождение Q1.1:

проверки атомиков и исходные 300 модульных проверок. Host-проверки выполнены с

Раздельные compile/link-наблюдения SQL, независимый PCUDA Q3.3 и матрица

### Архив B. Продолжение этапа 0: коллективные операции и SQL baseline

Это исторический отчёт первой версии измерителя. Исходные артефакты сохранены;
актуальная native-time методика и последующие прогоны — в [архиве C](REPORT.md#stage0-completion).

#### PCUDA reduction/scan и атомики

Команда полного прогона — в [архиве A](REPORT.md#stage0-readme); доступен отдельный запуск:

```bash
python3 test/pcuda_stage0/run.py --suite collectives --device-name 780M \
  --extra-flag=--gcc-install-dir=/usr/lib/gcc/x86_64-pc-linux-gnu/14.3.1
```

Фактический полный прогон: `build/pcuda-stage0/run-in0uieu3/report.json`,
AMD Radeon 780M, тот же AdaptiveCpp/LLVM/HIP, что в первом прогоне стенда.

- `runtime.hpp` — общие тестовые RAII-обёртки stream, typed GPU/pinned buffers
  и модулей; расчёт байтов с проверкой переполнения. Основной движок их не использует.
- `collectives.hpp`, `reduce_kernel.hpp` — коллективные операции и тестовые
  сигнатуры, **не утверждённый ABI SQL-модулей**.
- `block_reduce.cpp`, `block_reduce_unsigned.cpp` — SUM/MIN/MAX для `long long`
  и `unsigned long long`. Дерево в shared memory, нейтральные значения для
  неполных блоков; перед повторным использованием shared памяти есть барьер.
- `block_scan.cpp` — Hillis–Steele exclusive scan и суммы блоков; padded-потоки
  вносят нули, но участвуют во всех барьерах. `add_offsets.cpp` добавляет
  межблочные смещения. Каждый модуль содержит одно ядро и обёртку запуска.
- `collectives_main.cpp` — host-план иерархии scan: вверх до одного блока, затем
  вниз с добавлением смещений. Количество уровней рассчитывается по размеру,
  без фиксированного лимита `256³`. Буферы выделяются до измеряемых запусков и
  переиспользуются. Промежуточные суммы остаются на GPU, host читает их только
  после измерения для независимой сверки.
- `atomic_probe.cpp` — 32-bit Add/CAS/Exch и 64-bit Add/Min/Max/Or/CAS.
  Под конкуренцией проверяются единственный победитель CAS, счётчики и bitmap.
  64-битная часть запускается только при `pcudaHasAtomic64`; на 780M она прошла.

Проверено по 165 fixtures на вариант, всего **660**: блоки 32/48/64/128/256;
пустой вход, один элемент, границы блока и квадрата размера блока, переход через
куб размера блока, где позволяет выбранная ёмкость, и 1000003 элемента.
Достигнуты четыре уровня scan. Три набора значений: нули, разреженные единицы,
большие целые/смешанные знаки. Проверяются точность выше `2^53`, каждый prefix,
суммы блоков, SUM/MIN/MAX и poison-элемент за выходом, где есть свободная ёмкость.
До launch ограничены суммы и промежуточные значения дерева; проверяются размеры
выделений, свойства устройства, недопустимые указатели/block/default stream.

Вычислительные ядра поддерживают block до 256; host-иерархия требует block ≥ 2.
Проверенный максимум входа — 1000003, не произвольный предел устройства.
Снятие фиксированного предела старого MHT **не** означает, что уже проверены
размеры выше `256³` или исправлен старый MHT. Нужны дальнейшие нагрузочные тесты.
SQL NULL/3VL и типы параметров этими fixtures не моделируются.

Матрица `-O0`/`-O3` × PCH/без PCH: все результаты совпали; во всех 28 `.so`
полного стенда — по одному ядру, различные HCF object-id и допустимые имена.
`-DNDEBUG` применяется к host runner, проверки не основаны на `assert`.

Пример наблюдений на 1000003 элементах (мс):

| Вариант | Первое выполнение, block 32 | Warm, block 32 | Warm, block 48 | Warm, block 256 |
| --- | ---: | ---: | ---: | ---: |
| O0, без PCH | 275.928 | 1.889 | 2.603 | 2.519 |
| O0, PCH | 268.288 | 1.902 | 2.563 | 2.511 |
| O3, без PCH | 271.157 | 1.893 | 2.567 | 2.510 |
| O3, PCH | 263.950 | 1.883 | 2.573 | 2.513 |

Интервал включает всю иерархию scan, две signed/unsigned block-reduction
SUM/MIN/MAX и финальное ожидание, **не** время одного ядра. H2D, poisoning,
D2H и CPU-сверка исключены; барьеры перед/после нужны для границ измерения.
Первое выполнение включает device JIT. Warm — медиана трёх повторных fixtures
на том же размере для конкретного block. Atomics проверяются отдельно, не входят
в эти интервалы. Варианты работают в отдельных процессах с пустыми каталогами
device JIT на старте. Это одна серия, не SLA и не сравнение с SYCL-примитивами.

#### 2. Уточнённая методика и матрица PCH/O0/O3

По замечанию пользователя Python-измеритель исключён из измеряемых команд. Отдельной GNU
`time` в окружении нет; используется нативный Bash 5.3 `time` с
`TIMEFORMAT` и шестью знаками после запятой, `LC_ALL=C` для корректного JSON независимо от внешней locale. Python организует
серии и анализирует уже записанные файлы. `compiler_proxy.sh` — Bash, не Python.
Сам драйвер acpp в этой установке написан на Python: его необходимая работа
входит в native wall и не вычитается. Убран именно дополнительный Python-прокси,
а не overhead самого toolchain.
Времена внутри GPU-запроса по-прежнему измеряются C++ steady_clock на границах
синхронизации; native process wall дополнительно включает startup/data loading.

Флаги явно записаны в командах:

- Модули: C++17, generic PCUDA, `-fPIC`, `-O0`; `-O3` только контроль.
- PCH: `-fpch-instantiate-templates`, совместимый уровень оптимизации;
  затем `-include-pch`. Подготовка учитывается отдельно.
- `-g0` явно исключает отладочную информацию; сама исходная Release-сборка
  также без неё, отдельное ускорение от `-g0` не заявляется.
- Линкер: `-fuse-ld=lld`, контрольный `-Wl,-O0` (оптимизация размера ELF, не
  оптимизация GPU-ядра). Этот флаг не объявляется отдельно измеренным ускорением.
- `-ftime-trace=<owned file>` и `-Wl,--time-trace=<owned file>` — только
  диагностика, не ускоряющие флаги. Clang/LLD trace-поля анализируются отдельно,
  родительские и вложенные интервалы не суммируются.

`native_timing.py` отделяет native wall/user/system от Clang ExecuteCompiler,
Frontend/Backend и LLD ExecuteLinker. Исходные JSON сохранены для сортировки и
анализа. В SQL-режиме исходная/effective команда записываются раздельно. Host
движка не пересобирается с O0: сравнивается только его JIT toolchain.

команда, полный набор флагов, исходник/PCH и границы измерения. Уже доступные
пользовательские debug/PCH файлы не перезаписывались и не объявляются этим тестом.

Таким образом, первые девять пунктов этапа 0 выполнены (включая согласованный
типовой лимит/fallback и NULL из архива D), последний пункт согласования численных
критериев остаётся открытым по решению пользователя. До его закрытия этап 0
целиком завершённым не объявляется и этап 1 не начинается.

#### Финальная проверка стенда

- `run-g29n1lco`: исходные 300 модульных проверок, 660 collective fixtures и
  атомики повторно прошли уже на native time/lld с Clang/LLD traces.
- `types-bench-u9xg590e`: все 1971 проверки трёх моделей повторно прошли после
  обобщения тестового ядра; `types-bench-jt65z6d1`: 1305 проверок лимита 8 + fallback.
- `q33-bench-zwmltw8g`: девять результатов SF10 после дополнительной проверки
  отсутствия unsigned underflow в host memory guard.
- `sql-baseline-x9oby_nt`: Q3.3 × 3 через db_cli с нативным измерителем по
  умолчанию, без параметра `--native-time`; два вызова acpp (PCH и SQL).
- Все 11 CPU-тестов parser/trace/native-time/timeout, Python/Bash syntax,
  ссылки документов и `git diff --check` прошли. Код `src/`/`include/` не менялся:
  его SHA-256 сверены с полными SQL baseline-сериями.

Старый Python-измеритель удалён из SQL runner. `--native-time` оставлен как
совместимый параметр, но нативные таймеры теперь используются всегда. Исторические
raw отчёты не переписаны. Численные performance-пороги от этого не стали
утверждёнными; последний чекбокс остаётся пустым по решению пользователя.

<a id="stage0-types"></a>

### Архив D. Этап 0: эксперимент с независимыми типами параметров

#### Воспроизведение и границы

```bash
PYTHONDONTWRITEBYTECODE=1 python3 test/pcuda_stage0/types_bench.py \
  --series 3 --device-name 780M \
  --extra-flag=--gcc-install-dir=/usr/lib/gcc/x86_64-pc-linux-gnu/14.3.1
```

Артефакт финального повторного прогона: `build/pcuda-stage0/types-bench-u9xg590e/report.json`. Измерения —
нативный Bash time, Clang/LLD traces анализируются Python после работы процесса.
Host — Release/O3/NDEBUG; GPU-модули O0, PCH, `-ffp-contract=off`, lld/O0.
Контракция FP отключена для точной сверки порядка операций, не ради ускорения.
PCH подготовлен за 301.762 мс отдельно и не входит в cold first.

Это изолированный эксперимент, не параметризация SQL-движка и не новый ABI.
Проверены существующие числовые классы литералов Int64/Float64; другие SQL-типы,
строки, decimal и новые возможности не добавляются. Input — известный integer
тип; выражение `(input + p0) * p1 + p2` имеет **три независимых параметра**.

`typed_params_main.cpp` действительно вызывает компилятор/линкер при первом
запросе типа в lazy-режиме, а не подставляет сумму заранее измеренных времён.
Процессы запускаются через fork/exec с подготовленным argv; child делает только
exec/_exit. `native_command.sh` записывает времена без Python-измерителя в горячем
пути; собственный Python-драйвер acpp включён в native wall.
Модули и entry points кешируются в процессе, файлы прежнего процесса не
переиспользуются. Один модуль — одно ядро, имена включают типовую специализацию.
Уникальность kernel names/HCF ID проверена для каждого набора загруженных модулей.

Сравниваются:

1. **Lazy typed:** один отсутствующий модуль на впервые встреченный type mask.
2. **Runtime tags:** один модуль; каждый узел арифметики сохраняет Int64 либо
   выполняет требуемое смешанное преобразование в Float64.
3. **Eager typed:** все восемь допустимых вариантов готовятся до первого запуска.

Вход — 262147 строк, блок 128. Проверены все восемь сочетаний типов, ordinary
values, typed NULL одного/всех параметров, NULL в исходной колонке, три изменения
двух изначально равных, но независимых параметров. На стратегию/серию — 24 случая
× 9 запусков и три проверки независимости слотов. Все результаты сверены с
отдельными явными CPU-формулами для каждого порядка преобразований, без вызова
device helpers. Есть целые выше `2^53`; в частности, integer умножение до
прибавления floating p2 не заменяется ранним переводом всех значений в double.
Границы всех integer-промежуточных значений ограничены до launch.

Проверки остаются активны в Release. Все **1971** GPU-результата прошли
(9 процессов × 219 проверок); все validity-only изменения и обычные новые
значения дали нулевой прирост compiler/linker calls. Это пока не гарантия
параметризации полного SQL-пути: его перенос начинается только после этапа 0.

#### Результаты

Три серии, порядок стратегий ротируется. Новый device JIT-каталог на каждый
процесс, `ACPP_ADAPTIVITY_LEVEL=1` задан явно, OS caches не очищены.

| Модель | Cold first, медиана мс | Warm арифметика, медиана мс | Compile/link calls на все 8 схем | Сумма `.so`, байт |
| --- | ---: | ---: | ---: | ---: |
| Lazy typed | 248.784 | 0.262933 | 8 / 8 | 141216 |
| Runtime tags | 259.038 | 0.414665 | 1 / 1 | 18464 |
| Eager typed | 1461.312 | 0.261796 | 8 / 8 | 141216 |

Cold first начинается после загрузки fixtures, включает реальную подготовку
модулей, load/dlsym, первый device JIT, launch и fetch первого результата.
Для eager туда входит подготовка всех восьми модулей; для lazy — только первого.
Warm — kernel submission + synchronization, без D2H и CPU-сверки; медиана по
валидным наборам и восьми warm-повторам каждого типа. Это арифметический
микробенчмарк, его разницу нельзя механически переносить на время всего SSB.

Полная подготовка всех посещённых typed-схем: native compile около 680–695 мс,
link около 621–631 мс; runtime tags: 86.193 и 75.844 мс соответственно.
Typed NULL не добавляет вариантов. Совместимость числа параметров/типа результата
не угадывается по величине значения: tag/schema и validity отделены от payload.

#### Комбинаторный рост

В худшем случае один kernel с N независимыми параметрами двух числовых типов
имеет до `2^N` typed-вариантов:

| N | Максимум схем |
| ---: | ---: |
| 1 | 2 |
| 2 | 4 |
| 3 | 8 — фактически проверены |
| 4 | 16 |
| 8 | 256 |
| 16 | 65536 |
| 32 | 4294967296 |

Строки кроме N=3 — точный комбинаторный расчёт, **не измеренные** размеры/времена
больших запросов. Lazy устраняет предварительную подготовку непосещённых схем,
но не сам worst case. Eager переносит весь рост в cold first. Runtime tags
сохраняет один модуль ценой runtime-ветвлений. Validity известных typed NULL не
входит в ключ и не умножает это количество на дополнительные `2^N` вариантов.
Перевод всех integer-параметров в double для устранения роста неприемлем.

#### Согласованное решение и проверка лимита

Пользователь согласовал **lazy typed + tagged fallback**: до восьми typed-модулей
на структуру ядра, затем один универсальный tagged модуль. Уже загруженные
typed-модули сохраняются и переиспользуются; неподготовленные схемы после лимита
используют fallback, а не запускают бесконечную генерацию. Смена числового типа
может скомпилировать отсутствующую typed-специализацию либо единственный fallback.
Обычные значения и typed validity в ключ не входят. Межпроцессного SQL-кеша нет.

Пользователь согласовал NULL-правила: известный тип слота сохраняется при NULL, отдельно
передаётся validity; первый NULL выводит тип из однозначного контекста. Если
контекст неоднозначен, сохраняется NULL-only форма без выдуманного double-типа;
замена её на число может потребовать новую типовую схему. Существующая SQL NULL
функциональность при этом не запрещается. NULL-предикаты должны сохранять 3VL.
Это политика для последующей реализации; точный layout ABI всё ещё определяется
на этапе 2, а не этим экспериментальным Scalar/Parameters.

Дополнительная проверка согласованного ограничения:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 test/pcuda_stage0/types_bench.py \
  --bounded-four --series 3 --device-name 780M \
  --extra-flag=--gcc-install-dir=/usr/lib/gcc/x86_64-pc-linux-gnu/14.3.1
```

Артефакт финального повторного прогона: `build/pcuda-stage0/types-bench-jt65z6d1/report.json`. Здесь четыре
независимых параметра, выражение `(input + p0) * p1 + p2 + p3` и все 16 схем.
В каждом из трёх процессов реально созданы ровно 8 typed-модулей и 1 fallback,
ровно по 9 compiler/linker calls и 9 dlopen/dlsym-resolutions. Последовательность
новых компиляций по первым посещениям схем: девять единиц, затем семь нулей.
При NULL/изменении значений новых компиляций нет; возврат к первой typed-схеме
после создания fallback тоже переиспользует её модуль. Все **1305** проверок
прошли (16 схем × 3 validity fixtures × 9 запусков + 3 проверки независимости,
умноженные на 3 серии). Precision/mixed/NULL ожидания вновь независимые CPU-формулы.
Суммарный ELF размер девяти модулей 164184–164216 байт; отличие между сериями
связано с сериализованными HCF ID, а не с набором SQL-возможностей.

NULL-only вывод из контекста в движке пока не реализован: на этапе 0 требуется
согласовать политику, а не преждевременно выполнять этап 1. Существующие NULL
пути не изменялись и не запрещались этим решением.
