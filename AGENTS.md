## 2. Технологический стек и границы миграции

- **Язык:** строго C++17.
- **Целевой GPU-стек:** AdaptiveCpp Portable CUDA (PCUDA), `--acpp-targets=generic --acpp-pcuda`.
- **Сборка:** CMake.
- **Зависимости:** `linenoise` для CLI, `hyrise/sql-parser` для AST.
- Цель — полный перенос: ядра, память, stream, загрузка данных, служебные GPU-операции и ручные примеры. Постоянный гибрид SYCL/PCUDA и поддержка двух backend-реализаций не являются целью.
- В ещё не перенесённых участках временно сохраняется SYCL. Новый и переносимый GPU-код должен использовать PCUDA; не добавляй в него `sycl::*` или прямые/транзитивные зависимости от `sycl/sycl.hpp` через заголовки проекта.
- Предпочитай нативный `pcudaParallelFor`. Не вводи chevron launch или межмодульные вызовы device-функций без отдельного обоснования и проверки поддержки установленной версией AdaptiveCpp.
- Первичная аппаратная приёмка — AMD GPU. Не используй в коде движка предположения, нарушающие переносимость на NVIDIA/Intel в пределах возможностей AdaptiveCpp; не заявляй аппаратную проверку на недоступных устройствах.
- Согласованный compatibility seam этапа 3 — `src/core/pcuda_compat.cpp`: установленный публичный PCUDA wait теряет native result, а device properties не содержат CPU/GPU-признака. В production только здесь используется нижний runtime; перепроверять совместимость при обновлении AdaptiveCpp. `legacy_plan_runtime.cpp` сохраняет исторический SYCL launch-view только для ABI-negative fixture и не линкуется в engine. Не распространять эти исключения на новые примитивы/модули. При неподтверждённом teardown — fail-closed, без небезопасного free/unload.
- SF10 physical schema находится в `include/storage/ssb_schema.h`: Int32LE, ASCII '0'/'1' flags и FixedText; DDATE имеет 17 колонок. Числовые файлы читаются по полному размеру, flags расширяются в Int32 0/1. **2026-11-08 пользователь отверг словарную подмену и сначала поручил план 7-TEXT; 2026-11-10 — утвердил контракт и внедрение.** Первоначальный text rejection — историческая граница числового этапа, не текущее поведение. Raw-prefix/zero-tail сохранён только в историческом fixture. Manual SSB требует nonnullable input/unique dimension keys; SQL nullable/MHT/OR проверяется отдельными engine fixtures.
- **Контракт 7-TEXT, утверждённый 2026-11-10 и функционально проверенный на AMD 2026-11-11:** полный предложенный набор, включая COUNT/MIN/MAX Text; единый валидный UTF-8 Text с unsigned-byte сравнением, значимыми пробелами и отдельным NULL. Logical NUL, implicit Text/number/Boolean и SUM/AVG Text запрещены. FixedText декодируется до первого bounded NUL (хвост игнорируется), либо на всю ширину; nullable payload не интерпретируется. Предел значения INT32_MAX bytes, суммы/произведения checked 64-bit + memory guard. Compact bytes/offsets/validity, borrowed POD views и runtime-owned parameter arena; custom2 использует BUILDING/FURNITURE. CPU result владеет строками, CLI печатает JSON-quoted Text. [Исследование](test/pcuda_string_research/REPORT.md) и [точный ABI v2](test/pcuda_stage7/TEXT_ABI.md) сохраняют контракт/границы. LIKE/regex, функции строк, collation и новые join kinds не добавлены; исторические результаты не переписываются.

## 3. Целевая архитектура

### Разделение обязанностей

- Соблюдай SOLID и SRP: Presentation, планирование/Execution, JIT Compiler и Storage должны иметь явные границы ответственности.
- Целевой конвейер: SQL/AST → разрешение ссылок и выделение параметров → Logical Plan → Optimizer → явный физический план выполнения → поиск/генерация модулей ядер → компиляция отсутствующих модулей → загрузка и выполнение.
- План выполнения явно описывает запуски ядер, инициализацию буферов, зависимости, служебные копирования, обеспечение ёмкости, runtime-ветвления и циклы.
- Генератор GPU-кода не должен одновременно управлять памятью запроса, формировать host-алгоритм выполнения и извлекать результаты. Устраняй эту связанность при переносе `src/core/visitor.cpp`.

### Kernel Fusion и модули

- Единица раздельной компиляции — одно фактическое GPU-ядро вместе с его host-обёрткой запуска в одной единице трансляции; специализированное ядро загружается как отдельная `.so`.
- Не путай текущий `Pipeline` с одним ядром: некоторые pipeline и дополнительные code streams содержат несколько запусков и host-операции.
- Сохраняй слитые scan/filter/probe/aggregate там, где нет необходимого pipeline breaker. Раздельная компиляция не означает отдельное ядро на каждый SQL-оператор.
- Универсальные служебные ядра и PCH подготавливаются при сборке/установке. На SQL-пути компилируются только действительно специализированные отсутствующие модули.

### Параметры, ABI и кеш

- Отделяй структуру запроса от значений. Изменение совместимого значения, например `a > 10` → `a > 15`, не должно запускать codegen, `acpp` или линкер после подготовки шаблона.
- Операторы, выбранные колонки, порядок ключей сортировки и другие изменения логики остаются структурными. Сначала разрешай SQL-позиции вроде `ORDER BY 1`; не заменяй их обычными параметрами значений.
- Значения в WHERE, HAVING, арифметике, CASE и LIMIT должны параметризоваться. Размеры и выбор алгоритмов, зависящие от этих значений, рассчитываются при выполнении; не зашивай их в исходник или размеры статических массивов.
- Не объединяй независимые параметры только потому, что их текущие значения совпали. Не специализируй оптимизированную программу по текущему значению обычного параметра.
- Целевой ABI модулей — единая фиксированная C-сигнатура с версионируемыми POD-структурами, без STL и SYCL-объектов. План хранит привязку слотов аргументов к колонкам, буферам и параметрам; загрузчик проверяет версию и схему аргументов.
- **ABI v1 утверждён на этапе 2 (2026-11-05) и заморожен:** `include/core/module_abi.h`, `module_contract.h`, C11/C++ assertions и [отчёт](test/pcuda_stage2/REPORT.md). Этапы 5–7 до Text использовали entries v1. **С 7-TEXT весь native SQL-путь, включая числа, использует ABI v2**: `module_abi_v2.h`, `module_contract_v2.h`, фиксированные `db_kernel_{identity,descriptor,launch}_v2`, namespace SHA-256. Scalar — 16 bytes, argument — 56, invocation — 80; [полный контракт](test/pcuda_stage7/TEXT_ABI.md). Не приводить аргументы v1 к v2 и не интерпретировать legacy queue как stream. Изменение layout/семантики требует новой версии. Legacy entries остаются только в negative fixture; whole-query `execute_query(ExecutionContext*)` и bundle compiler в engine отсутствуют.
- На этапе 0 согласованы lazy typed-специализации Int64/Float64 (до 8 на структуру ядра) и один tagged fallback после лимита; готовые typed-модули сохраняются. Смена типа может компилировать отсутствующий вариант/fallback. Typed NULL сохраняет тип слота и меняет validity без компиляции; первый NULL выводится из однозначного контекста, иначе сохраняет NULL-only форму, для которой замена на число может потребовать новой схемы. **Этап 5 реализовал bounded cache и runtime ABI-параметры; этап 6 проверил 16 схем четырёх независимых параметров для predicate, fractional arithmetic, arithmetic+CASE и COUNT/HAVING при фиксированном output ABI/layout (8 typed +1 fallback на family), смену Int64/Float64 выходов и typed NULL.** Общий тип CASE сохраняется и в fallback; новый типовой план может потребовать lowering, но готовый fallback не требует нового module source/build. Это не обещание девяти модулей для произвольного меняющегося output layout; общая функциональная приёмка остаётся этапам 7–8. Не расширяй SQL-систему типов автоматически.
- **Согласованная на этапе 6 числовая семантика:** SUM/MIN/MAX используют Int64 либо Float64 входного выражения, COUNT — UInt64, AVG — Float64. Не возвращать unsigned-накопление signed/fractional SQL-выражений или определение существования группы по одному ненулевому агрегату. UInt64 у COUNT не разрешает unsigned-преобразование отрицательного SQL-операнда: mixed signed/unsigned арифметика и сравнения точны через внутренний знак/модуль, без double и без нового SQL-типа. Минус перед числовым литералом нормализуется до выделения параметров; общий унарный оператор над колонками/выражениями и Float64 GROUP BY CASE не добавлены. Новая политика Int64 overflow/деления на ноль не вводилась.
- `QueryTranslator::prepare` разрешает ссылки и выделяет параметры до оптимизации. Не передавай обычные значения оптимизатору: engine понижает параметризованное дерево и передаёт значения через ABI; кеш плана учитывает структуру, schema и каталог, но не SQL spelling/значения. `bindLegacyPlan` сохранён только для совместимости исторических host-тестов, не для native SQL-пути. Не возвращай value-specialized lowering под новым value-free ключом.
- Кеш модулей и разрешённых entry points — только внутри процесса. Не добавляй постоянный кеш скомпилированных SQL-модулей без запроса пользователя. Готовый PCH является артефактом сборки, а не таким кешем.
- Ключ модуля учитывает его структуру, схему аргументов, ABI и существенные настройки компиляции; обычные значения параметров не входят в него. Временные артефакты должны иметь явного владельца и не конфликтовать между сессиями.
- Внутренний device JIT AdaptiveCpp — отдельный слой. Отсутствие вызова SQL-компилятора движка не доказывает отсутствие работы device JIT.
- Текущий timing model — `pcuda-modules-v1`: используй явный `--timing-model pcuda-modules-v1` в benchmark runner и [его границы](timing.md#этап-5-pcuda-modules-v1--2026-11-07). `compile_ms` — direct parallel build elapsed, native compile/link sums экспортируются отдельно; отсутствие codegen/acpp/link/dlopen/dlsym доказывается счётчиками. Исторический `explicit-plan-v1` допускал warm lowering; не изменяй его raw/gates задним числом. `codegen_ms` новой модели сам по себе не доказывает полный бюджет SQL→PCUDA ≤10 мс.

## 4. Жёсткие ограничения

### Полнота и безопасность типов

- Никаких заглушек: код должен компилироваться и работать; не оставляй `TODO: implement this` или пропущенную реализацию.
- Проверяй переполнение размеров, смещений, счётчиков, сложений и произведений до выделения памяти или запуска ядра.
- При умножении больших неотрицательных величин расширяй тип **до** умножения, например `(unsigned long long)left * right`; одного расширения левого операнда достаточно. Не применяй unsigned-преобразование механически к знаковой SQL-арифметике.
- Не заменяй все числовые параметры на `double`: это теряет точность больших целых. Сохраняй согласованную семантику типов, преобразований и NULL.

### Ресурсы и производительность

- Вся GPU/host-pinned память, stream и загруженные модули управляются RAII-обёртками. Аллокации и освобождение принадлежат runtime-менеджерам, а не генерируемым модулям ядер. В неперенесённом коде не расширяй существующие нарушения этого правила.
- Используй переиспользуемые result/scratch-буферы и High-Water Mark. Не допускай неконтролируемой избыточной ёмкости больших аналитических результатов.
- С 7-TEXT удерживаемый HWM-workspace принадлежит одному активному value-free плану: совместимые значения/typed NULL и немедленные повторы переиспользуют его; другая структура/схема освобождает старые scratch/result owners через RAII. Совпадение имени scratch/номера колонки не отождествляет два плана. Process-only план/module/entry cache при этом не очищается. Не обещать zero-allocation после произвольной смены SQL.
- Минимизируй системные вызовы, поиск имён и загрузку библиотек в горячем пути. Повторно используй загруженный модуль и найденную функцию запуска.
- Применяй Predicate Pushdown: фильтры должны предшествовать дорогим операциям, когда это разрешено SQL-семантикой; не проталкивай предикаты через join ценой изменения результата.
- Сохраняй GPU-резидентность промежуточных данных. Не добавляй host-материализацию вместо корректного GPU-пути без обоснования.
- Для динамически генерируемых PCUDA-модулей используй `-O0`; обычный host-код остаётся в Release. Контрольные сравнения уровней оптимизации допустимы, но не переноси вывод о JIT-ядрах на весь движок.
- Пути toolchain и параметры компиляции должны конфигурироваться, а не содержать привязку к машине разработчика. PCH должен соответствовать compiler/flags/headers и не пересоздаваться безусловно при старте `db_cli`.

### Порядок выполнения и ошибки GPU

- Используй один явный упорядоченный PCUDA stream для зависимых операций запроса; не полагайся на default stream. В неперенесённом SYCL-коде очередь остаётся `in_order()`.
- Копирования и инициализацию ставь в тот же stream. Асинхронная копия на хост требует ожидания **перед чтением данных CPU**, а не лишнего барьера перед её постановкой.
- Синхронизация обязательна перед освобождением используемой памяти и выгрузкой используемого модуля. Сохраняй время жизни host-буферов и аргументов до завершения использующих их операций.
- Не вставляй ожидание после каждого ядра. Дополнительные барьеры допустимы только с обоснованием зависимости, управления ресурсами, диагностики или измерения.
- Проверяй коды ошибок PCUDA и ошибки асинхронного выполнения на соответствующих границах ожидания.
- Не предполагай фиксированный warp size, доступность FP64/64-битных атомиков или произвольный размер блока; проверяй требуемые возможности устройства.

Неполное/отсутствующее покрытие, неподдержанный GPU-путь и границы whole-function/targeted-анализа указывай явно; host coverage не является device coverage. ### Обязательная методика performance-измерений

- Время процессов измеряй нативным Bash `time` или GNU `time`, если он доступен; внутренние интервалы — C++ `std::chrono::steady_clock` с необходимой синхронизацией GPU на границах. Для машинных результатов фиксируй locale и единицы измерения.
- Python допустим для организации серий вне измеряемого интервала и offline-анализа готовых JSON/traces. Не используй Python как таймер, компиляторный прокси или дополнительную исполняемую обёртку внутри измеряемой цепочки; не выполняй online-анализ во время измерения.
- Собственная работа Python-драйвера `acpp` входит в native wall time и не вычитается. Не смешивай её с накладными расходами дополнительного Python-измерителя.
- Обязательно используй Clang `-ftime-trace` и LLD `--time-trace` для диагностики. Сохраняй исходные trace-файлы; анализ выполняй после измеряемых команд. Эти флаги не являются ускоряющими.
- Проводить сопоставимые повторные серии с traces и без traces обязательно: диагностика сама может добавлять overhead. Показывай её влияние отдельно, а не вычитай предполагаемый overhead из исторических результатов.
- Не складывай вложенные trace-интервалы, wall time процесса и его дочерних процессов как независимые компоненты. Не называй весь остаток между wall time и trace-полями исключительно временем драйвера: туда могут входить запуск процессов, ожидания, I/O и неохваченная диагностика.
- Фиксируй число повторений, порядок/ротацию вариантов, сырые значения, медиану и разброс. При недостаточной выборке не заявляй статистически подтверждённый выигрыш. Не складывай медианы компонентов для получения медианы общего времени.
- Различай cold шаблона запроса, cold процесса и cold device JIT. Записывай состояние каждого кеша: новый каталог device JIT в начале сессии не означает пустой кеш перед каждым следующим запросом или очищенный OS cache.
- Первое выполнение может включать device JIT; если его время отдельно не наблюдается, не выдавай разность cold/warm за чистое время JIT.

### Интервалы и обязательная колонка summary

В performance-таблицах показывай следующие величины раздельно, с явными единицами и границами:

| Показатель | Что измеряется |
| --- | --- |
| Компиляция | Native wall/user/system вызова `acpp -c`, включая работу драйвера; подготовка PCH отдельно |
| Линковка | Native wall/user/system отдельного вызова линковки; если старый путь объединяет compile/link, так и обозначай, не называй его чистой компиляцией |
| Загрузка модулей | `dlopen`, регистрация модулей, `dlsym` |
| Первое выполнение и fetch | GPU-выполнение с необходимым ожиданием и возможным device JIT; получение результата CPU показывается отдельно |
| Полный старт процесса | От запуска приложения до готового CPU-результата первого запроса; отдельно показывай startup, подготовку, загрузку данных и первый запрос |
| **summary** | От передачи первого запроса движку в уже загруженной БД до готового CPU-результата: prepare/codegen, необходимые compile/link, load, first execution и fetch |
| Warm | Повторное выполнение; время самого исполнения и полный путь запроса не смешиваются |

- `summary` — пользовательская cold-задержка первого запроса в **уже загруженной БД**. Startup, загрузка исходных данных, независимая проверка результата, форматирование и печать в неё не входят. Полный старт процесса — другая метрика, а не альтернативное определение `summary`.
- Измеряй `summary` одним непрерывным интервалом. Сумма отдельно измеренных compile/link/load/execute/fetch может быть дополнительным `component_sum`, но не заменяет прямое измерение `summary` и не скрывает промежутки между операциями.
- Если прототип не выполняет SQL parse/plan/codegen, явно указывай это у его `summary`; не объявляй такую величину end-to-end SQL latency. После интеграции необходим замер реального SQL-пути через `db_cli`.
- Проверку вычислений выполняй вне измеряемого прогона, например независимым Python/CPU-oracle. Не используй те же device helpers как единственный oracle и не включай его работу в `summary`.
- Методику и поля отчётов согласовывай с `timing.md` и runner при их изменении; документация новых правил сама по себе не означает, что существующие измерители уже исправлены.

## 6. Формат и организация отчётности

- Каждый этап имеет отдельную папку и **один основной `REPORT.md`**. Для самостоятельного исследования действует такое же правило. Пример целевого расположения этапа 0: `test/pcuda_stage0/REPORT.md`.
- Только при реальной необходимости допустимы **один–два дополнительных тематических `.md`** в папке этапа/исследования; объясни необходимость и дай ссылки из `REPORT.md`. Они не должны дублировать итоговый отчёт или служить журналами его продолжения.
- Не создавай для каждого этапа отдельные `RESULTS.md`, `COMPLETION.md`, повторные итоги, отчёты на каждый прогон/набор флагов или цепочки «продолжений». Обновляй соответствующие разделы основного отчёта.
- `todo.md` хранит задачи, зависимости и статусы; `AGENTS.md` — обязательные правила. Команды, stdout/stderr, сырые JSON, traces, PCH и бинарные результаты отдельных прогонов сохраняй в каталогах артефактов с идентификаторами и ссылками из отчёта, а не в новых Markdown-файлах.
- При обновлении отчёта сохраняй историю измерений и изменения методики. Новое измерение не переписывает старое задним числом; историческая неуспешная проверка не становится успешной из-за смены oracle или агрегации.

### Обязательная структура REPORT.md

1. **Статус и границы:** выполненное, невыполненное, ограничения и блокирующие задачи; не путать готовность стенда с интеграцией в движок.
2. **Окружение и конфигурация:** версии compiler/runtime/LLVM/линкера, устройство, хеши исходников/PCH/бинарников, полные исходные и effective команды/флаги, существенные переменные окружения.
3. **Методика:** границы интервалов, единицы, состояние кешей, прогрев, порядок вариантов, число повторений, режим диагностики и исключённые из измерений операции.
4. **Результаты:** сопоставимые таблицы с `summary`, медианами и разбросом; ссылки на все сырые измерения и traces; явно отмеченные несопоставимые случаи и отсутствующие данные.
5. **Корректность:** независимый oracle, число проверок, несовпадения, ограничения; не скрывать неудачи общим `success`.
6. **Выводы и решения:** отдельно подтверждённые факты, гипотезы, отрицательные/нейтральные результаты и согласованные пользователем решения.
7. **Воспроизведение и оставшаяся работа:** команды, артефакты, незакрытые вопросы и критерии завершения.

3. **Отобрать и проверить кандидатов.** Исследовать PCH и инстанцирование шаблонов, frontend, codegen, оптимизационные проходы, параметры AdaptiveCpp, выбор и параметры линковки. Для исключённых кандидатов записать причину: неприменимость, отсутствие поддержки, нарушение семантики или отсутствие отношения к измеряемому пути.
4. **Измерить влияние.** Сначала изменять один фактор, затем проверять обоснованные сочетания. Фиксировать baseline и хеши входов, совместимость PCH/флагов и состояние кешей; повторять серии с ротацией порядка, а не сравнивать случайные лучшие прогоны.
5. **Проверить цену ускорения.** Для кандидата показывать влияние на native compile/link, trace-фазы, `summary`, первое и warm-выполнение, размер модулей и корректность. Сохранять отрицательные/нейтральные результаты. Флаг, нарушающий точность или SQL-семантику, не считать допустимым ускорением; экспериментальные флаги не переносить в движок автоматически.
6. **Измерить реальные границы.** Отдельно показать подготовку PCH, компиляцию, линковку, загрузку, первое выполнение, fetch, полный старт процесса и непрерывный `summary`. Текущий `q33_bench.py` вычисляет `cold_module_path_ms` суммой отдельных измерений: это компонентная оценка, не готовый прямой замер `summary`.
7. **Доказательный отчёт и согласование.** Сохранить воспроизводимые команды, все исходные данные, объяснение различий с историческими результатами, конфигурации и нерешённые гипотезы. Исходные предложения и последующее явное решение пользователя от 2026-10-31 различаются в разделе 6 отчёта; завершение экспериментов само по себе не означало утверждения порогов.

### Уже установленные факты для начального разбора

- В сохранённых сериях сопоставимый **SQL Q3.3, O0/PCH** имеет native `acpp` wall median **2775,087 мс** в `sql-matrix-oe5qo0yx` и **2771,103 мс** в `baseline-series-g4b_dmw4`; cold SQL total — **3447,548** и **3368,742 мс**. Бинарник и записанные хеши исходников совпадают. Не представляй это как многократное различие скорости компиляции одного пути.
- Существенно различается cold host fetch: **90,113** против **0,582 мс**. В матрице Q3.3 — первый запрос процесса, в полной серии перед ним идут восемь запросов с общим внутрисессионным состоянием; большая fetch-задержка там наблюдается раньше, на Q2.1. Прогрев общего служебного ядра компактизации — объясняющая гипотеза, требующая отдельного подтверждения, а не уже доказанная причина.
- Команды не полностью одинаковы: матрица явно задаёт `-Wl,-O0`, полная серия — нет. Контролируй это различие и не приписывай ему всю разницу без измерения.
- **1027,076 мс PCUDA-прототипа** и **3368,742 мс полного SQL-пути** не являются измерениями одинаковой реализации: прототип использует компактные 24 группы, не выполняет SQL parse/plan/codegen и имеет другие границы cold. Совпадение SF10-результата не делает их одинаковыми алгоритмами; такое сравнение не доказывает эффект одних только флагов или смены SYCL на PCUDA.
- Исходные данные этих сравнений находятся в `build/pcuda-stage0/q33-bench-knd6vwtl/report.json`, `build/pcuda-stage0/sql-matrix-oe5qo0yx/report.json` и `build/pcuda-stage0/baseline-series-g4b_dmw4/report.json`. Если артефакт недоступен, явно сообщай об этом, не восстанавливай доказательства из одного пересказа.
- В новых контролях PERF-COLD порядок Q2.1 → Q3.3 воспроизвёл уменьшение fetch Q3.3 с около 75 до 0,94 мс при одинаковом `-Wl,-O0`; отдельный runtime-log подтвердил cache miss/hits общего ядра компактизации. Это подтверждает reuse, но не измеряет чистое время device JIT и не приписывает ему весь fetch. См. основной отчёт, раздел 4.7.
