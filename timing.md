# Методика измерения времени запросов

Этот документ описывает тайминги, которые используются при экспериментальных
запусках Crystal-SYCL. Измеряемое время запроса охватывает полный путь SQL
внутри прототипа: от передачи SQL-строки движку до получения результата в памяти
CPU.

Загрузка исходных данных не входит во время запроса. Базовые таблицы загружаются
в память GPU до серии экспериментов и относятся к подготовке окружения. Ввод
команды пользователем, вывод строк в терминал, форматирование результата для
печати и запуск процесса также не входят в измеряемые интервалы.

## Основные интервалы

Основная измеряемая величина:

```text
total_query_ms =
    prepare_ms
  + codegen_ms
  + compile_ms
  + library_load_ms
  + generated_execute_ms
  + host_fetch_ms
```

Эти интервалы должны образовывать разбиение одного непрерывного диапазона
времени. Один и тот же участок не должен попадать сразу в два интервала, а между
соседними интервалами не должно оставаться неизмеренных промежутков.

| Поле | Что измеряет | Границы измерения |
| --- | --- | --- |
| `prepare_ms` | Разбор SQL, построение структуры запроса, оптимизацию, вывод формы результата, типов и имён столбцов, предварительную проверку памяти GPU, подготовку начальных result-буферов, вычисление ключа JIT-кэша и проверку кэша. | От начала обработки SQL до завершения проверки JIT-кэша и начала генерации кода либо запуска найденной библиотеки. |
| `codegen_ms` | Генерацию специализированного C++/SYCL-кода для подготовленного плана. | От начала обхода плана генератором до получения строки с исходным кодом. |
| `compile_ms` | Динамическую компиляцию сгенерированного кода. | От начала вызова компилятора до получения пути к `.so`. Включает запись `.cpp` и запуск AdaptiveCpp. |
| `library_load_ms` | Загрузку динамической библиотеки. | `dlopen`, поиск `execute_query` через `dlsym` и подготовку указателя на функцию. |
| `generated_execute_ms` | Выполнение сгенерированной функции `execute_query(db::ExecutionContext*)` целиком. | От входа в сгенерированную функцию до завершения её работы, включая финальный барьер очереди. |
| `host_fetch_ms` | Получение результата на стороне CPU. | От завершения generated execution до полностью заполненного `QueryResult` в CPU-памяти. |
| `engine_ms` | Работу движка до получения результата на CPU. | `prepare_ms + codegen_ms + compile_ms + library_load_ms + generated_execute_ms`. |
| `total_query_ms` | Полный путь SQL-запроса внутри прототипа. | От входа в `DatabaseInstance::executeQuery` до готового CPU `QueryResult`. |

`generated_execute_ms` не является чистым временем одного GPU-ядра. В этот
интервал входит CPU-side отправка задач в SYCL-очередь, выделение или повторное
использование scratch-буферов, инициализация временных буферов, все
сгенерированные GPU-ядра, необходимые `q.wait()`, небольшие служебные копирования
внутри сгенерированного кода и освобождение временной памяти.

## Cold и warm JIT

В экспериментах нужно различать два режима.

| Режим | Состав времени |
| --- | --- |
| Cold JIT | `prepare_ms + codegen_ms + compile_ms + library_load_ms + generated_execute_ms + host_fetch_ms` |
| Warm JIT | `prepare_ms + library_load_ms + generated_execute_ms + host_fetch_ms` |

Cold JIT соответствует первому запуску запроса, когда сгенерированная библиотека
ещё отсутствует в кэше. Warm JIT соответствует повторному запуску того же SQL,
когда библиотека найдена в кэше. В warm-режиме `codegen_ms` и `compile_ms` должны
быть равны `0`; если расширенный timing-вывод был отключён, benchmark JSON
нормализует отсутствующие timing-поля в `null`.

## Совместимые имена полей

Benchmark runner сохраняет несколько старых или UI-ориентированных имён для
обратной совместимости.

| Каноническое поле | Совместимое поле |
| --- | --- |
| `codegen_ms` | `code_generation_ms` |
| `compile_ms` | `acpp_compilation_ms` |
| `host_fetch_ms` | `result_materialization_fetch_ms` |
| `engine_ms` | `engine_processing_ms` |
| `generated_execute_ms` | `gpu_execution_ms` |

`gpu_execution_ms` оставлено только как alias. Оно равно
`generated_execute_ms` и не должно трактоваться как время одного GPU-ядра.

## JSON-файлы benchmark runner

`olap_bench/tools/run_olap_bench.py` записывает канонические timing-поля в каждую
измеренную строку `summary.json` и дополнительно сохраняет совместимые поля из
таблицы выше.

Для проверки разбиения интервалов каждая строка также содержит производные поля.

| Поле | Что означает |
| --- | --- |
| `engine_component_sum_ms` | Сумма `prepare_ms`, `codegen_ms`, `compile_ms`, `library_load_ms` и `generated_execute_ms`, если все эти поля присутствуют. |
| `engine_minus_components_ms` | `engine_ms - engine_component_sum_ms`, если оба значения присутствуют. |
| `timing_component_sum_ms` | Сумма всех шести основных компонентов, включая `host_fetch_ms`, если все поля присутствуют. |
| `timing_total_minus_components_ms` | `total_query_ms - timing_component_sum_ms`, если оба значения присутствуют. |

Небольшие ненулевые расхождения допустимы из-за точности таймеров и округления
при печати.

`aggregate_summary.json` считает средние значения по каждому каноническому
timing-полю и по производным consistency-полям. В агрегацию входят только
успешные measured-запуски без timeout.
